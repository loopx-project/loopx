# 汇报规范（REPORTING）

这是管家工作区的默认汇报规范。由自然语言指令（如“汇报”）或已启用的周期性报告任务消费；本文只定义证据核验、编辑结构与引用边界，本身不是新增 CLI、自动调度或权限授予。

## 默认口径

当用户说“汇报”（不带额外限定）时，直接执行一次全局汇报，不先反问范围或是否开始。

- 默认使用中文与当前会话或订阅声明的本地时区（未声明时默认 `Asia/Shanghai`）。单次交互式“汇报”默认回顾前一日 `00:00` 至本轮证据读取截止时刻，并核对当前状态；明确说明统计起止时刻，不将其混同为滚动 24 小时窗口。
- 覆盖当前受众授权目录中的全部活跃 Goal，与界面当前选中的单个项目无关。只使用已声明且获准的证据源；没有实际读到的来源必须单列为覆盖缺口，不得算作已覆盖或“无进展”。已停止的 Goal 仅在用户明确要求查看历史／停止事项、或固定周期全景日报合同要求时纳入。
- “汇报今天／本周／某项目／需要我处理”等限定问法，按指定的日期、项目或问题缩小范围，并延续当前对话中的目标、约束、已授权决定与未完结交付。

## 证据要求

1. **完整分页读取**：按需分页读取来源目录（`sources`）、适用 Goal 的阶段与里程碑（`portfolio`）、当前及近期已完成任务（`todos`），以及统计窗口内的交付记录（`deliveries`）。将交付记录关联回对应任务的具体目标与结果，不能只看最新一条而掩盖窗口内的前序成果。
2. **严格区分生命周期阶段**：优先说明实际产物、用户可感知路径、发现的反例、修复及真实采用。严格区分计划、代码提交、请求送达、接收方读取、接收方采用、实际执行、独立验收与用户侧最终拿到结果；阅读回执、文件落盘或代码合入均不能替代端到端结果验证。
3. **区分证据等级**：明确区分本轮独立核验事实、Agent 记录声明（如 `observed_reality`、`checkpoint_reason`）与分析推断。检查交付记录的验证类型、证据引用与字段覆盖；记录写入时间不自动等同于实际完成时间。
4. **外部状态先验真再提请决策**：在建议用户执行合并、批准、授权、解除阻塞或操作外部账户前，必须核对决定该事项的当前权威外部状态。历史遗留的 `open`、`waiting`、过期草稿或 `closed-but-unmerged` 记录本身不能证明当前仍需用户行动；无法实时核实的外部条件应列为待负责 Agent 对账的未核实依赖，不重复索取已有授权。
5. **保留既有交办归属**：对已发出的交办核对原请求回执与返回记录，保留原负责人与原对话返回路径。已送达的请求不重发，已验收的结果不重做；一次汇报本身不会自动发起新的任务委派。
6. **诚实标注覆盖边界**：明确说明未读、陈旧、脱敏、超限、读取失败或跨页版本变化带来的结论边界。缺少运行记录不等于没有进展；缺少金融或外部执行回执不等于已经成交、平仓或风险消除。
7. **成本独立记账**：涉及成本时分别说明预算上限、已观测实支与未知部分。不得凭上下文字节缩减、测试通过或调用次数下降去推算未经实测的账单金额、运行延迟、模型得分或科学净收益。

## 输出结构

先给出统计窗口与最重要的整体判断，再按对决策最有用的顺序组织正文：

- **交付与影响**：什么已经实际改变、在哪里能看到、解决了什么问题，注明对应的验证层次。
- **仍欠的结果**：当前所处阶段、具体剩余缺口、负责角色与已有可继续路径。覆盖所有适用 Goal，相关事项合并叙述，不用裸任务 ID 清单或任务条数代替实质内容。
- **需要本人处理**：严格区分阻塞推进的必做决策、普通非阻塞事项与 Agent 可自主推进的工作。说明各选项的影响与建议顺序；若核实后当前没有新的必做决定，直接明确写“当前无新增待拍板事项”。
- **依据与覆盖**：列出可用的来源链接、实际读取版本或记录时点、统计窗口及未覆盖材料缺口。公开代码或文档引用须绑定已核验的仓库与确切修订；私有证据仅保留受众内可读说明，绝不上传或改造成公开外链。

按事项复杂度控制篇幅，优先使用短段落、短列表，仅在多项并列对比时使用紧凑表格。完整汇报正文必须留在当前对话中，外部文档或附件不能替代正文。

## 信息密度、排版与可点击引用

- **结论与因果先行**：开头交代统计窗口与全局判断，再按业务主线组织短段落；将重要成果、关键反例与残余缺口放在相邻位置对照呈现，不把内部机器字段、裸哈希或验证流水账直接堆进正文。
- **保留前后量化对照**：写明原本什么失败、修改后行为如何变化、适用版本、实际部署／安装采用状态，以及关键前后指标对照（保留单位、比较方向与负向反例）。不同模型、不同预算、不同代码基线或不同阶段的观测结果必须注明条件差异，不得混称为同源因果增益。
- **统一声明共性边界**：一般性的读取范围与共性证据限制在开头或末尾覆盖说明中集中交代一次，仅在局部存在材料冲突、关键未知或适用范围变化时就地补充，避免每条成果后重复同一句免责声明。
- **公开对象一律附完整可点击链接**：凡正文中提及公开仓库的 PR、Issue、Release、Commit 或工作流运行记录（尤其是可合并 PR 清单、停滞 PR 清单与待决策关联项），一律写成完整可点击的 Markdown 链接（例如 `[#123](https://github.com/example-org/example-repo/pull/123)`），不得只写裸编号 `#123` 或 `#123@deadbeef`。引用前须核对目标仓库与对象真实存在，不臆测组织名或分支。
- **结构化日报拆条保链**：在受单段字数上限约束的结构化报告（如 `periodic-report` 单条 `summary` 或 `detail.text` 的 `360` 字符上限）中，若需列出多条带链接的 PR 或事项，必须拆分为多条 `details`（每条控制在 3–4 个带链条目）或拆成独立 `item`，严禁为压缩字数剥离超链接；公开 GitHub 条目的 `source_ref` 优先绑定已核验的 `https://github.com/...` URL，`sha256:` 摘要仅用于本地非公开证据溯源；私人记录使用角色、记录日期与主题标明出处，不伪造外链。
- **窗口内外严格分列**：重新核验发现的窗口内事实可补实当期判断；统计窗口截止之后发生的合入、采用或修复如需提及，必须单列为“窗口后补充”并注明时点，不得静默改写原窗口口径。

## 边界

汇报只执行授权范围内的读取、核验与综合分析，不创建 Goal、不修改 Todo、不启停 worker、不执行合并／发布／金融动作，也不自行安装定时任务。若用户在同一轮额外提出具体的修改或执行指令，按当前会话既有的授权工作流独立处理。

## 周期性全局汇报执行口径

当管家工作区已通过 LoopX 的 typed 订阅接口启用周期性全局汇报（`periodic-report`）时，按以下规则运行（本节定义生成口径，实际启用状态、下次到期时点、暂停与投递回执一律以系统 typed 配置与宿主回执为准，不手写平行调度账本）：

- **固定半开统计窗口**：对每个计划截止时点 `T`，严格汇总固定窗口 `[window_start, T)` 内本机受众授权的全部 Goal（含活跃与已停止 Goal；停止项可合并说明，但不得标为已完成或自动恢复）。计划截止时点 `T` 与实际开始、生成完成、消息送达时间分别记录，不将模型耗时或离线补报冒充准点投递。
- **到期必报（不套用变更静默跳过）**：周期性报告属于固定日历交付；即使窗口内无新增业务交付，到期也必须生成报告，明确说明“本期无新增完成项”并列出当前在办与仍欠结果，不得套用普通变更监控的 `quiet`／`no_change` 规则跳过当期报告。
- **观察、生成与投递分离**：未到期前的轮询观察不调用模型；冻结生成与原会话投递分别校验与记账。同一窗口沿原身份幂等恢复，已确认送达的窗口绝不重复发送；投递结果未知时先读回原投递回执，不盲目新建会话或重跑生成。
- **离线缺报恢复**：短时离线恢复后补齐最近一个完整到期窗口并注明延迟；跨多个周期离线时，默认只生成最新一个完整到期窗口的报告，同时在报告中显式列出错过的历史缺报区间（`missed_cadence`），不将缺报窗口伪标为已交付，也不在恢复瞬间并发拉起多个历史窗口的模型任务。
- **权限与配额隔离**：周期性报告复用既有调度、`periodic-report` 与原会话返回链路，不得借用业务项目的 worker 身份、任务租约或项目执行额度，也不得压占正常高优业务任务与到期重规划。
