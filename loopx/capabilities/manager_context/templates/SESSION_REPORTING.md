# 单项目周期汇报规范（SESSION REPORTING）

这是单个受管 Goal 会话（`ManagedSessionReports`）在未提供项目自定义 `REPORTING.md` 时使用的默认汇报规范。本文只定义本 Goal 冻结证据范围内的核验、结构与引用要求，不授予跨项目读取或状态变更权限。

## 范围与证据边界

1. **严格限定本 Goal 授权范围**：只使用当前 Goal 已冻结的任务记录、里程碑与获准读取的产物；不访问其他 Goal、全局组合视图或未声明的外部来源。
2. **区分采集时刻与窗口完成时刻**：任务列表在采集时观察，必须依据原生完成与证据时间戳严格区分本期窗口 `[window.start_at, window.due_at)` 内的新增成果、当前在办事项、更早历史成果以及窗口截止后的后续变化；时间戳缺失或未知时保留为未知，不得臆测。
3. **区分任务完成、独立验证与消息送达**：原生 Todo 标为 `done`、代码提交或本地产物落盘，与独立结果验证及原会话消息实际送达属于不同阶段；保留失败、阻塞、回退与不可读记录，不得只报喜不报忧。
4. **到期必报**：即使本期窗口内无新增完成项，到期仍须如实生成简明报告，交代当前在办进展、阻塞原因与下一步计划，并将报告生成任务本身排除在业务进展计数之外。

## 正文结构与可点击引用

- **整体判断先行**：开头直接说明本期统计窗口与本 Goal 的核心进展判断，再展开关键交付、问题因果、阻塞缺口与下一步行动；将共性证据边界集中说明一次，不在每个条目下重复套话。
- **保留具体前后对照**：写清改了什么、验证到了哪一层、指标或行为如何变化（保留单位、比较方向与失败反例），避免用裸 `todo_id`、哈希值或“持续推进中”代替实质结论。
- **公开对象一律附完整可点击链接**：凡提及公开仓库的 PR、Issue、Release、Commit 或工作流运行记录，一律写成完整可点击的 Markdown 链接（如 `[#123](https://github.com/example-org/example-repo/pull/123)`），不得只写裸编号 `#123` 或 `#123@deadbeef`。
- **结构化字段拆条保链**：在 `periodic-report` 单条 `summary` 或 `detail.text`（`<=360` 字符）等受字数上限约束的字段中，若包含多条 PR 或交付清单，必须拆分为多条 `details`（每条控制在 3–4 个带链条目）或独立 `item`，严禁为省字数剥离超链接；公开 GitHub 条目的 `source_ref` 优先绑定已核验的 `https://github.com/...` URL，本地非公开证据使用任务或摘要引用，绝不伪造外链或外泄私有材料。
