# Freshness 评测报告：常规场景与目标变更场景

本报告合并两个场景中已选定的 main 与修复后 freshness 数据，只使用各次运行的原生评分与原始用量账本。它是一次诊断结果汇总，不是正式榜单成绩、重复实验结论或 freshness 单一机制的因果证明。

**目标变更场景中，修复后 freshness 更早发现并采用新需求，原始分数较高；常规场景中，main 原始分数较高。两次 freshness 最终都异常退出，因此质量表现与运行可靠性必须分开判断。**

English summary: This report combines one unchanged-task diagnostic comparison
and one silent goal-change comparison. The repaired freshness snapshot has a
higher original score in the goal-change scenario and a lower original score
in the unchanged-task scenario. Both treatment runs remain `runner_invalid`.
All four runs remain unqualified for countable score claims. Different complete
source snapshots, a historical target baseline, single attempts, incomplete
economic cost and evaluator sensitivity limit attribution. No aggregate win
rate, leaderboard result or general superiority claim is made.

所有运行均保持 `score_countable=false`、`matched_pair_countable=false`。
严格运行时隔离，尤其是求解器 shell 与模型提供商凭据的隔离，没有获得

可进入正式榜单。两次 freshness 均保留 `runner_invalid`，不改写成成功。

## 3. 目标场景：运行中静默替换完整需求

最初任务是离线 OpenAPI 兼容性比较接口与命令行工具；约第 900 秒，
受保护的权威需求文档静默替换为报告基础设施、校验后 hook、pytest
集成、示例生成与格式/覆盖控制五个目标。两边都要自行读取变化并调整工作。
评分器始终按照最终需求评分；需求变化前的提交也使用同一评分器。
实际发布延迟分别为 901.005 秒与 901.370 秒。

examples；hooks、pytest 和 generation 仍有缺口。完整通过阶段数分别

没有给最终归档追加评分，因此分数仍属于原始提交。

### 3.2 从读取变化到实际采用

以下时间均从新需求发布开始计算：

| 行为 | main | 修复后 freshness |
| --- | ---: | ---: |
| 首次完整读取新需求 | 958.439 秒 | 45.559 秒 |
| 首次明确确认需求变化 | 985.457 秒 | 44.588 秒 |
| 首次成功修改新需求源码 | 1,707.271 秒 | 638.543 秒 |
| 后续实际实施模块 | hooks、writers、pytest | hooks、writers、pytest、examples |

freshness 在 22.288 秒时已从普通交付结果上下文接触新需求标题，随后
确认变化，再完整读取文档，所以确认略早于完整读取。两侧均未观察到
`provider_revision_mismatch` 返回，不能把提前感知解释成一次过期依据硬拒绝。

旧任务被替换时，freshness 保留了原 Turn 的身份；原轮次的结果、方向
与额度结算完成后，才进入新的实施任务。随后多个模块产生源码、验证与
原生评分。这支持本次真实运行走通了原轮次结算和后续采用，不能只凭
新建任务或写出重规划记录宣称成功。最终评分缺口仍然保留。

main 保留已有初始任务实现后推进新需求；freshness 将初始候选保留为
独立检查点，再恢复原源码推进新需求。初始实现本身不满足新需求，但
通用探测经验可能复用；不能把变化前全部 token 等同于浪费。

### 3.3 终态失败

main 共 10 条宿主回执，包含一次模型容量不足和尾端超时，之后仍继续
推进并最终退出 0。退出 0 不表示全部新需求通过验收。

freshness 共 9 条宿主回执，其中三次失败均已调用宿主、退出 1，且未
标记超时；明确错误是模型容量不足。最后一次发生在自主重规划阶段，
原操作效果无法确定，外部调度 worker 为避免重复执行而保留
`replan_outcome_unknown`，最终求解器退出 2。此时距原生上限尚余
344.011 秒，因此这次目标场景的停止原因是容量错误与未知结果恢复边界，
不能归为预算耗尽。两侧都未观察到合成凭据造成的宿主调用前拒绝。

## 4. 常规场景：完整原题始终不变

完整报告与校验增强任务从首次指令保持到终态；没有初始替代任务、定时
发布器或中途需求编辑。main 后 freshness 串行各跑一次。两次求解和
原生评分均已终态，分别产生 10 份与 12 份原生评分报告，共 22 份。

### 4.1 原生质量

| 原评分阶段 | main | 修复后 freshness | 权重 |
| --- | ---: | ---: | ---: |
| Hooks | 11/12 | 11/12 | 2 |
| Report writers | 12/14 | 13/14 | 2 |
| Pytest reporting | 3/8 | 3/8 | 3 |
| Examples | 9/9 | 9/9 | 2 |
| Email / body generation | 10/10 | 5/10 | 1 |

freshness 在 writers 多过一项，在最后阶段少过五项。两边最佳与最新
源树不同，但最新原始评分的生产源码与最终归档逐文件一致；没有把未评分
的最终代码当成额外提升。main 完整通过 2/5 阶段，freshness 为 1/5；
这些阶段完成比例不是 76.7262% / 73.1548% 的加权分数。

终态后的源码与既有静态检查语义比对提示：两边都实现了邮箱域名转小写，
但内部辅助函数命名不同，部分隐藏检查对该名字敏感；五项失分与这个差异
吻合。因此不能直接把五项失分描述为五项业务功能没做。该解释仍是静态
推断，缺少本次逐检查错误日志的直接确认；原始分数没有修改，也没有重跑
评分器。公开报告不包含隐藏检查实现、函数名或原始评分输出。

### 4.2 实际推进与未完成结算

freshness 在启动后有实际任务完成与后续模块实施，不是仅接通启动；
但这些过程事实不证明质量收益。原题没有变化，本场景也没有提供测量
“发现需求变化并正确采用”的机会。

连续六轮工作后触发周期性重规划。模型发现报告配置从 True 更新到
False 的问题，形成验证记录和后续方向；发现问题不等于已经修复。
重规划写回成功，但返回仍要求登记本轮额度消耗并完成结算。约四秒后
宿主超时，退出码 124；轨迹和持久事件未见对应结算完成。

调度器保留了“该重规划已启动”，但自己的记录没有完整原轮次结算身份；
模型后来补齐的身份没有同步回调度器记录。恢复代码只处理带完整身份的
记录，因此跳过了这次恢复。防重复保护随后阻止用新轮次重做未知操作，
以 `replan_outcome_unknown` 停止，求解器退出 2。源码中的预算收尾
预留与模型临近截止才写回共同形成时间窗口；实际恢复仍有缺口。
这不是已经自动恢复成功，也不是一次需求版本过期拒绝。

main 末尾也有宿主超时，但后继预算耗尽唤醒未调用宿主，worker 最终
退出 0。常规场景的 freshness 运行状态保持无效；其原始评分仍可作为
这次提交的诊断观察，不能因此升级为有效运行。

## 6. 结论、验证与后续边界

- 目标变更场景支持这次样本中更早读取、确认与实际采用新需求，以及较高
  原始质量分数；它没有证明正式有效成绩或稳定可靠续行。
- 常规场景中 main 原始分数较高；freshness writers 略多通过、未缓存输入
  和输出较少，但总 token 略多，且末轮结算失败。命名敏感检查限制了分差
  的功能解释。
- 两次 freshness 的停止触发不同：目标场景是模型容量错误，常规场景是
  宿主超时；两者都暴露未知重规划效果的恢复边界，不应混成同一故障原因。
- 单次样本、历史参照、不同完整源码快照、串行时序、未资格隔离及未知
  完整费用，都限制因果和经济结论。不发布跨场景总体胜负或普遍收益。
- 质量、持续控制、完整结算和运行有效性分别核对；保留失败及未测区别，
  不以进程退出码、任务数量、测试通过数或记录写回替代需求验收。

本报告复用终态后的原始评分、源码核验和响应账本分析。目标场景 18 份、
常规场景 22 份原生评分均保留原值；没有启动新求解、替补运行或额外 judge。
公开内容仅含经整理的汇总数字、通用机制观察与源码版本，不含原始任务、
私有运行标识、会话、凭据、隐藏检查或机器路径。私有证据保留用于授权
审计；本文不是第三方可独立重放的公开实验包。

后续修复应让调度器在启动重规划前持久化完整结算身份，并在原身份下
恢复尚未完成的步骤，同时给临近截止的重规划留下收尾时间。还需分别
确认评分接口的兼容性、当前默认产品入口的采用和重复运行表现。这些是
当前证据指出的待验证方向，本次整合没有把它们记为已修复或已通过。
