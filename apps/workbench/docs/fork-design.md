# 分叉（Fork）与接力继续设计说明

本文档记录 LoopX Workbench 对「分叉」「接力继续」及「按话题侧边栏聚合」的交互取舍，以及支撑「接力继续采用 0-Token 成对锚点」这一底层策略的对照实验数据。

## 一、设计结论

1. **交互上把两类直觉彻底拆清：「分叉」与「接力继续」**
   - **分叉（Fork）**：回归 Codex / Claude Code 的原生直觉——点击回复底部的分叉图标（`⑂`）即**一键复制原对话完整历史**（点击中间某轮则截断到该轮），打开副本后停在原地等你沿着另一条思路往下问，不自动发消息；点击顶栏或侧栏菜单里的「分叉」可顺手勾选 `独立 git worktree` 或附带首句。
   - **接力继续（Handoff）**：承载「清空冗长上下文 / 换 Agent 或模型 / 运行中并行开线 / 额度耗尽续跑」场景。入口收在回复底部 `⋯`、顶栏 `⋯`、侧栏右键、`/` 命令与额度耗尽卡片，打开 Codex 风格单一输入胶囊（可自由切换 Agent / 模型与可选 worktree）。界面不出现「轻量分支」「省 Token」「0 压缩等待」「进度锚点」等实现术语。
   - 当会话正在运行中或底层 Agent 不支持原生分叉时，点击回复底部 `⑂` 会平滑落到「接力继续」胶囊卡，不留死胡同。

2. **侧边栏按话题统一聚合，用 12px 极小单色图标区分衍生类型**
   - 主列表只保留独立「话题」；由该话题衍生出的 **原生分叉（`⑂`）**、**接力继续（`⇄`）**、**划词/消息追问** 与 **团队协作** 全部自动归入父话题的折叠抽屉，每条子项标题前用 12px 极小单色线性图标一眼区分。
   - 任何衍生子线程在侧边栏右键菜单中均支持「移出为独立话题」（`PATCH /api/threads/:id { forkGroup: null }`），长大后随时可独立为主线。

3. **接力继续的默认实现：新会话起步 + 0-Token 成对进度锚点 + 按需回查 `loochat history`**
   - 接力继续不复制源会话的全量历史，也不调用额外模型做压缩或写交接摘要。
   - 在新会话首轮消息发送时，由 daemon 在本地用 0 额外模型调用生成一个结构化 `<loochat-fork-anchor>` 进度锚点（仅作为发送给 Agent 的系统上下文，不在用户气泡里展示），内容包括：
     - 源对话最近 3 轮的**成对问答摘要**（用户要求 + 助手结论），避免只放用户原话导致「方案 A」「把这个改一下」等指代失去参照；
     - 源对话近期修改/涉及的文件路径；
     - 回溯完整上下文的明确命令：`loochat history <sourceThreadId> --turns 6`（按成对轮次查看，而非只看用户输入）。
   - 额度耗尽（`plan_exhausted`）触发的自动续跑直接复用同一机制，自动接管中断轮次与排队消息，并移除主动定时压缩与预生成交接摘要流程。

## 二、为什么「接力继续」不复制全量历史，也不用小模型先写摘要？

在长对话（150K–500K tokens）中途切分支或换模型时，直觉上常见的几种方案各有隐患：

- **直接复制全量历史**：
  - 无法跨 Agent / 跨提供商工作；
  - 源会话正在运行中时往往无法安全分叉；
  - 对不支持跨分支共享前缀缓存的模型或提供商，首轮会重新计费整段长历史；
  - 历史中的旧方案试错与过期工具输出持续占据上下文窗口。
- **只放一条「自己去查历史」的指令**：
  - 模型刚起步缺乏坐标，容易先做多轮盲查，拉长端到端耗时并增加无效读盘。
- **先用便宜模型生成 30 行结构化交接摘要**：
  - 有额外的摘要模型开销与等待时间；
  - 更关键的是「二次转述失真」：抽象总结容易把关键概念区分、临时约束或刚否决的方案压扁，导致接手模型误以为摘要已经完整而不再核对原文。

为了验证真实效果而不拍脑袋，我们设计了一轮本地只读对照实验。

## 三、受控对照实验

### 1. 实验设计

- **样本**：选取 4 条真实长会话，在存在强指代（「方案 A」「这个改一下」等）与中途否决约束的真实中途切点截断：
  - **样本 1**：移动端多方案界面取舍（切点第 22 轮，约 288K tokens）
  - **样本 2**：长周期评测根因分析与写作约束（切点第 44 轮，约 481K tokens）
  - **样本 3**：产品交互概念辨析与边界界定（切点第 8 轮，约 174K tokens）
  - **样本 4**：多提交代码回归定位与边界防御（切点第 16 轮，约 351K tokens）
- **评测方式**：
  - 每个样本在运行前预先冻结 4 条二元验收检查点（共 16 个检查点），覆盖事实准确、保留中途否决约束、正确消解指代、无编造结论；
  - 4 个策略组使用同一主模型、同一只读工作区与同一条真实后续需求，共跑 **16 次独立试验**，盲评打分并统计完整 Token、延迟与工具调用轨迹。

### 2. 四组对照策略

| 对照组 | 策略 |
|---|---|
| **Arm 0（裸新会话）** | 直接开新会话，不提供历史回查通道 |
| **Arm 1（纯指令）** | 新会话，仅告知通过 `loochat history`（成对问答）查看历史并继续 |
| **Arm 2（0-Token 锚点，最终采用）** | 新会话 + 本地 0-Token 注入最近 3 轮成对问答锚点与变更文件 + `loochat history --turns 6` |
| **Arm 3（模型预摘要）** | 先用轻量模型阅读源会话生成 30 行 6 节交接摘要 + `loochat history` |

### 3. 汇总结果（4 样本 × 4 组 = 16 次试验）

| 指标 | Arm 0 裸新会话 | Arm 1 纯指令 | **Arm 2 0-Token 锚点（采用）** | Arm 3 模型预摘要 |
|---|---:|---:|---:|---:|
| 验收检查点得分 | 11 / 16 | **16 / 16** | **15 / 16** | 14 / 16 |
| 幻觉 / 编造次数 | 0 | 0 | **0** | 0 |
| 平均端到端耗时 | 338.8s | 452.1s | **326.4s** | 299.8s |
| 主模型总调用轮次 | 73 | 45 | **36** | 42 |
| `loochat history` 调用次数 | 0 | 40 | **38** | 27 |
| 磁盘文件读取次数 | 233 | 50 | **30** | 40 |
| 非缓存输入 Token | 1,210,201 | 503,794 | **396,860** | 423,927 |
| 缓存命中读取 Token | 11,693,281 | 2,937,084 | **1,711,473** | 2,404,864 |
| 主模型总输入 Token | 12,903,482 | 3,440,878 | **2,108,333** | 2,828,791 |
| 主模型输出 Token | 109,215 | 85,230 | **81,873** | 81,738 |
| 平均峰值上下文 | 287,928 | 123,901 | **97,293** | 102,489 |
| 预摘要额外开销 | 0 | 0 | **0** | 524,912 输入 + 28,058 输出 |
| 折算有效主模型消耗 | 3,228,154 | 1,349,601 | **1,076,587** | 1,179,085（未含预摘要） |

### 4. 关键发现

1. **Arm 2 在质量、成本与速度上取得最优平衡**
   - 相比 Arm 0，主模型总输入 Token 下降 **83.7%**，平均峰值上下文从 ~288K 降至 **~97K**，且避免了强指代样本彻底失联（Arm 0 在强指代样本得分为 0/4，并被迫执行了 233 次全仓读盘）。
   - 相比 Arm 1，主模型总输入 Token 再降 **38.7%**，平均耗时缩短 **27.8%**（326.4s vs 452.1s），LLM 调用次数（36 vs 45）与磁盘读取（30 vs 50）均最低。
   - 相比 Arm 3，Arm 2 不仅省去预摘要模型的 525K 输入 + 28K 输出及起跑等待，主模型自身输入 Token 反而更少（**少 25.5%**），且得分更高（15/16 vs 14/16）。

2. **模型预摘要（Arm 3）出现「摘要失真导致漏检」**
   - 在概念辨析样本（样本 3）中，预摘要压缩掉了两个相近概念的边界区分，主模型信任摘要后减少了对原历史核对（`history` 调用从 38 次降到 27 次），导致该样本得分跌至 2/4。
   - 相比之下，0-Token 锚点直接引用原话片段并附带 `loochat history --turns 6` 指针，既给出坐标又不伪装成全貌，模型在需要细节时会主动回查原文。

3. **成对问答（`--turns`）是必要条件**
   - 仅拼接用户历史输入（`--user-inputs`）会产生大量无头指代（「选方案 a」「把上面那段删了」），只能用作定位目录；默认检索指令必须拉取成对的「用户提问 + 助手回答」。

## 四、两种操作的适用分工

- **分叉（`⑂`）**：从当前或中间某轮精确复制完整上下文，沿着另一条思路探索，或同 Agent 短对话直接沿用原生会话状态；需要隔离改动时从 `⋯ → 分叉` 勾选 `独立 git worktree`。
- **接力继续（`⇄`）**：对话过长、需要切换 Agent / 模型、当前线程仍在运行中想并行开线、或额度耗尽时使用，以 0-Token 进度锚点 + 按需 `loochat history --turns 6` 秒开新会话。
