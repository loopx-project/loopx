重试一次操作，可能把副作用做两遍；读回一张成功回执，也可能恢复早已过期的执行权。而当长程 Agent 与 Agent 团队连续运行数小时乃至数天时，只有存储原子性远远不够：按条件续跑（resume_when）、后台观测（continuous_monitor）、保留谱系的自主重规划、对等协作交接，以及模型逐字节消费的 CLI 标准输出，必须服从同一套类型化状态机。

1. 强模型参与的，是这些跨边界的语义问题

我们把强能力模型用在设计、实现和评审里，尤其是跨文件、跨 runtime 的假设检查。真正难的部分往往是：几个局部判断都对，组合起来却允许错误的执行顺序。8、9 月的核心 PR 已经反复遇到这类问题；它们不是迁移收尾后的补丁。

副作用已经发生，记录还没写下：重试会不会做两遍？

假设 provider 已执行成功，进程却在写 checkpoint 前崩溃。只检查 journal，会看到“未完成”；直接重试可能重复执行。相反，把所有不确定都当作成功，又会吞掉尚未发生的工作。这不是一个 try/catch 能解决的问题。

8 月 22 日的 #3485 在执行前持久化 prepared attempt 和稳定的 effect identity。恢复先询问 provider：确认已提交，就补记原结果；确认不存在，才按同一身份执行；结果未知，就停在待恢复状态。 对 effect 顺序、receipt 前缀和身份的检查同时保留。这里没有承诺任意外部系统都能 exactly-once：能否确认原结果，仍取决于 provider 的恢复能力。

它接续了 #3464 的 preflight：执行前判断“能不能做”，中断后判断“是否已经做过”。两者共同保护一次完整操作。只把 Python 函数逐个翻译成 TS，保不住这两个时间边界。

9 月 13 日的 #4286 把七类 Todo 操作的回执恢复收敛到一个 owner，并保留了更细的区别。假设两个 Agent 同时修改任务：A 先提交，B 因版本冲突被明确拒绝；随后 B 查回执时断网。后一次读取失败，不能抹掉前一次明确拒绝。 若断连发生在提交响应返回前，结果才需要保持未知，并沿原 operation identity 恢复。

这两条路径最后都可能遇到网络错误，下一步却不同。共享实现只尝试一次写入，随后读取原回执；对应回归分别检查明确拒绝、提交结果未知和准确回执恢复。统一错误处理不能丢掉错误发生的阶段，也不能把已知事实降成未知。

领取任务和取得执行权，必须是同一件事

两个 Agent 同时看到一个未领取任务。如果 claim 已写入、lease 尚未取得，中间状态究竟归谁？如果旧 Agent 曾成功领取，租约过期后又拿着旧 receipt 回来，它还能继续写吗？

从 #3529、#3669 的协调基础，到 9 月 6 日的 #4032，领取、租约和操作回执被纳入同一次条件提交。#3798 的 store 负责原子持久化，领域 owner 判断身份、作用域和合法转换。回执证明过去那次领取成功；当前租约与 epoch 才决定现在能否执行。 操作重放要能找回原结果，却不能复活已失效的执行权。不同存储中的 revision 也不能与领域版本或 lease epoch 混用。

这解释了为什么“幂等”不是把旧成功结果返回就结束。正确恢复既要记住历史，也要服从现在的权威状态。早期 foundation、shadow 和生产路径的资格是分阶段建立的，不能把第一个接口合入日写成所有后端都已投入使用。

修正一条证据，为什么会重新触发已经结束的工作？

规划更新尤其容易出现看似无害的默认值错误。用户只修正一条证据，没有改监控状态；如果更新逻辑用缺省值重建整个对象，已经满足的 monitor 可能被重新启用。与此同时，调用方显式传入空列表或 false，也不能被当作“没有提供”。

9 月 10 日的 #4178 将规划更新收敛到同一份权威快照和完整 TS transaction：省略保留原意，显式清空按字段与权限解释，证据修正不重新武装已满足的 monitor。它还删掉了 Python 合成 Markdown 再解析回状态的路径。这既是边界收敛，也是行为修复，不能笼统宣称逐字迁移、行为完全不变。

Song 后续的 #4433、#4494 把这种检查延伸到词表的定义、实际生产与消费：一个枚举能编译，不代表所有调用方都在表达同一个含义。前文的 skip / quota_skip 和 action / decision 分离，属于同一条语义主线。

怎样约束模型给出的“看起来正确”

让模型先指出错误假设，再构造会推翻它的执行序列：提交后断连、旧 lease 重放、只更新证据、显式清空。随后检查真实 owner、provider 和调用入口。

强模型帮助把散在各处的条件连起来；反例、真实存储与拒绝路径约束它的答案。目前没有逐 PR 的模型型号对照，不能据此量化某个模型的独立收益。我们能展示的是这些机制怎样改变，以及为什么需要改变。后来的 #7145 运行时路由、#7269 原 Turn 收尾是这条主线的延续，不代替前中期的核心工作。

2. 先还原历史：从迁移方案到面向 Agent 的语义内核

正式迁移 RFC 在 8 月 15 日合入。前 62 天至 10 月中旬，工程完成了事务与共享权威地基，并在 #6396 集中退役普通旧 Markdown writer；此后 41 天至 11 月 27 日——累计 103 天、2,126 个触及 loopx/control_plane/ 的合并 PR——第二轮收敛把这套事务底座推进成了直接服务长程 Agent 与 Agent 团队的完整语义控制面。

3 位开发者与各自 Agent 接力的 #6396 既是前两个月工作的收口，也为后续演进扫清了障碍：统一的 C1 轮次信源、可组合的 resume / monitor / replan 与对等交接语义、零 AST Any 词表棘轮，以及面向 Agent 的原生 CLI 均建立在这一地基上。

其中，新 maintainer Song（@songoow） 从 9 月中旬持续推进 Semantics RFC、词表收敛、生产证据和检查器修复。这条主线与事务、长程任务原语及 CLI 设计紧咬在一起。

LoopX 保存长程 Agent 与 Agent 团队的目标、任务、证据与执行边界。模型可以提出新路线，控制面负责保护版本、执行权和状态提交，并在中断后定位合法的恢复位点。

最初的大量实现是 Python，TS 的宿主、Pi 集成与 dashboard 已经存在。通过一次 Python 调用来做决策，再把结果接回 TS，是自然的起点。随着规则增多，默认值、状态解释、调用顺序和持久化开始分散在两边。

我们希望这些控制面规则有清楚的 typed owner，同时让 CLI、宿主和 App 共享同一套合同。103 天的实际演进可拆为以下交错推进的阶段。

3. Effect Program 先行：先统一“做过什么”

第一次有界切换发生在 8 月 21 日的 #3416。TS 接下 Effect Program、settlement algebra、Turn journal 的解释，以及持久 checkpoint effect。

这组边界之所以连在一起，是因为恢复要回答同一个问题：这笔工作有哪些 effect，哪些已经发生，下一个合法动作是什么？

一个 checkpoint 不能只是“把 JSON 写回文件”。操作身份、同键互斥、旧内容匹配、原子替换与持久化顺序，都影响重试能否识别原结果。把这些规则拆在多个运行时，下一次修恢复就要同时追几份实现。

因此这次切换把内部 effect 及其规则交给 TS。Python 保留兼容调用和 callback/provider 边界。托管的本地 runtime 按需启动、空闲退出，使用私有 token 与源码指纹处理生命周期；调用者不必手工管理一套 daemon。

这项设计也有成本。PR 中同一历史 checkpoint 工作负载的测量如下：

路径 p50 p95
旧 checkpoint 0.755 ms 2.020 ms
新的持久 checkpoint 路径 12.597 ms 18.610 ms

新路径增加了 RPC 与 durability 工作。这个比较说明第一次切换付出了什么，不能推导“TS 比 Python 慢”或今天整个 CLI 的延迟。先承认成本，才有条件检查后续完整事务是否消除了更多往返和重复判断。

4. 迁移完整事务：一次少到两次，也可能是正确答案

8 月 22 日的 #3447 明确停止继续平铺叶子 helper。原因很实际：每搬一个函数都加 facade、DTO 和 parity 脚手架，Python 仍决定组合顺序，生产链反而变长。

新的单位是一笔可观察事务。比如 Turn settlement，需要把输入解码、身份、journal、待执行 effect、结果归约和 closeout 放到一个 owner 下。Todo completion 同样牵动准入、状态、lease、continuation 和提交回执。

#3464 把 settlement 的 7 次叶子 runtime 调用收敛成粗粒度 turn.settlement.reduce。已交付切片中的路径是：

新 provider 工作：TS preflight → Python provider / checkpoint → TS final reduction
原结果重放：     TS reduction / 原结果恢复

两次与一次，分别对应有新 provider 工作和重放。图中的职责也不代表整个 CLI 只会发生这些调用。

评审曾发现一个有诱惑力的错误优化：只保留最后一次 reduction。这样调用更少，但畸形身份或 journal 可能直到外部 provider 执行之后才被拒绝。最终保留 preflight，由 TS 先授权准确的待执行 effect，Python 只执行这些 effect，再返回最终归约。

这个负例让我更看重“检查放在什么位置”。一个正确判断，如果发生在不可逆 effect 之后，也可能保护不了用户。

后续 task lease、Vision、monitor-poll、spend/void 等切片也沿完整事务推进。迁移账本需要记录：旧规则删了什么；新 bridge 加了什么；happy/recovery path 跨几次运行时；哪些脚手架可以退役；完整入口的正确性和延迟怎样。代码净增可以有理由，但要说清楚多出的代码承担什么。

5. 共享权威：把分布式存储原语接到 Agent 执行语义

事务迁移时，共享权威也在发展。从 wchwawa 推进的协调核心、aggregate/provider 与可恢复 reference，到 #3798 的 TS AuthorityStore，逐渐收敛出一个 provider-neutral 的持久化合同。

这里的关键是把两类问题分开：

  1. 领域 owner 判断一次状态迁移是否合法、谁有执行权。
  2. store 保证条件提交、持久化结果与证明的读取。

当前 AuthorityStore 提供 storeIdentity、loadAuthority、commitAuthority、readReceipt、scanCommitted 等操作。store 原子地保护 head、事件和回执；领域规则不能悄悄移进某个数据库 adapter。

几种版本必须分别解释：

标识 保护的边界
provider_revision provider 上的一次条件提交；其表示对领域调用方可以不透明
authority_revision 领域权威状态的版本
lease_epoch 一轮执行权的代际，防止旧 executor 继续写
store identity / lineage 当前读取的是否仍是同一条权威历史
operation identity / receipt 是否为同一笔已生效操作，原结果是什么

例如 PostgreSQL 在 COMMIT 后断连，结果可能已经持久化。provider 必须区分 missing、unavailable、failed 与 ambiguous durability。不能因为客户端没有收到成功，就当成没有提交。后续按原操作身份查 receipt，才有机会安全恢复。PostgreSQL candidate 的边界 也明确保留了部署与采用资格。

早期 Python executor 有 reference/coverage 作用，后来未使用的 prototype 被删除；实际 native File/SQLite 路径成为对应资格验证对象。保留过渡实现有期限，不能让 reference 悄悄变成第二套生产权威。

当存储提交遇上跨小时的 Agent 执行

当真实多小时运行的 Agent 持续读写 AuthorityStore 时，将纯存储提交原语与领域状态机严格剥离，接住了四类跨会话边界：

  • 按精确 GoalRef 隔离历史确认序（#8975）：同名 goal_id 重建后的多个实例共享同一条 rollout 日志。若不把历史 autonomous_replan_ack 的写回序绑定到精确 GoalRef（goal_id + goal_instance_id），已退役旧实例的刷新或压缩记录会误清 writeback_follows_admission，把当前活跃实例尚未完成的重规划审查静默抹掉。
  • 同代租约续期后保留已准入轮次的结算资格（#9257）：长轮次中途续期 hard_lease 会递增租约版本号，但并未改变执行归属。结算层现允许在同一 lease_epoch 与 idempotency_key 下，当 current_proof.expected_version >= requested_proof.expected_version >= admitted_version 时放行首次合并写回，同时对独立调用的 refresh-state 维持严格的当前版本 CAS。
  • 3 小时默认任务租约与失租无扣费收尾（#9304、#9314、#9342、#9487）：托管认领与租约的默认 TTL 从 45 分钟上调至 3 小时（10,800s），不改写既有租约回执。亚秒级“获取→释放→重领”保留毫秒级因果时钟（admittedAt <= acquired <= updated <= now，#9314）；spend-slot 摘要冲突直接返回原轮次守卫重检命令（#9342）；一旦原执行租约过期或被其他 worker 接替（#9304、#9487），observeFencedExecution() 只授予零配额消耗的管理态失租收尾证明（delivery_outcome: "outcome_gap"），绝不诱导 Agent 续跑已失效的执行代际。
  • 共享增量稀疏数组修复、2 万+提交快照与清晰的 Apache-2.0 云端 SPI（#8747、#8759、#8765、#9380、#9223）：在 File 与 SQLite 共用的增量日志（authority_state_log.ts）中，JavaScript 稀疏数组空洞持久化成 JSON null 后会被 .map()/.slice() 跳过，破坏摘要还原；#9380 统一改用 Object.hasOwn 逐下标比对修复。远端路径上，#8759（见归档前历史 postgresql_authority_store.ts）引入每 64 次提交周期快照、增量回放与租户级 RLS，验证跨越 20,000 次提交的恢复，并配齐强租约围栏下的远端任务结算（#8747、#8765）。最后，#9223 将服务端 PostgreSQL 存储与 RemoteAuthorityService 抽离至 loopx-cloud，在 Apache-2.0 核心仓完整保留本地 File/SQLite 权威实现、AuthorityStore SPI，以及本地私有 Goal 零远端触网、故障默认关闭（fail-closed）的出站网关合同。

6. SQLite 之后：长程历史也要有成本模型

LIHUA919 的 #4121 把可选 SQLite provider 接到既有 TS authority 合同。一次事务原子提交 head、receipts、events 和 outbox；claim/lease 的领域语义仍从原 owner 来。

接入数据库以后，还有三个不同的工程问题。

第一，当前 head 的成本不能跟总历史一起长。 #4408 把每次保留完整 projection 改为经过验证的周期 checkpoint 与已提交 delta，收敛 codec owner，提供事务性、幂等的旧格式迁移。当前读取、恢复连续性和完整审计有不同的读取范围。

第二，写入量要测对。 #4778 分别观察 logical write volume、窗口内累计 WAL 流量和应用观察到的锁等待。最终数据库文件多大，不能替代写放大测量；一次 rehearsal 也不能直接叫容量或持续运行验收。

第三，replay 的对象所有权会影响正确性。 #4931 减少未改变子树的复制、排序、编码，以及 receipt lookup 中无用的完整 projection 构造。同时保证返回给调用方的对象被修改后，不会污染下一次 replay 的内部基础状态；持久证明字节也保持不变。

这轮优化在一些路径上有明显收益，但大状态、扫描延迟和内存成本仍有缺口，PR 保留了未达到的目标。把这些差异留下，比给所有路径写一个统一“性能提升”更有用。

10 月的 #5805 又更新了未配置的新建 Goal 默认值，选择 canonical SQLite 与 hard lease。已有 Goal、显式选择和旧 operation retry 继续遵守各自合同。新建默认值、旧数据迁移、旧 writer 退役，是三件发生在不同阶段的事。

到 11 月初的 #7834，sqlite_v0 进一步接管了已完成与已替代 Todo 的归档权威（todo_archive 表）：在 todo complete 与 todo supersede 提交事务内自动将超出有界窗口（最近 N = 5 条终态项）的历史项迁入 SQLite 归档，使活跃 ACTIVE_GOAL_STATE.md 投影体积与完整历史解耦，同时保留按 ID 精确回读与恢复回执的能力。

7. Song 的 Semantics 与零 Any 内核收敛

新 maintainer Song（@songoow） 从 9 月 15 日的 #4433 发起并实现 Semantics RFC、registry 和提交路径检查，之后持续推进收敛。这条线让我们开始系统约束“概念怎样增长”。

跨语言迁移很容易产生重复知识：同名状态在 Python Enum、Literal、TS as const、展示层和判断分支中各出现一次。即使今天字符串一样，明天也可能有一处多加了值或换了解释。

Semantics RFC 将检查拆为可追溯关系：定义 owner、值域、生成绑定、producer、interpreter/projection。运行时从类型化 owner 取规则，登记表做约束与检查，不成为线上规则的另一个来源。

一个字段混入四种东西

#4494 处理过 effective_action 的混用：quota 决策、frontier 动作、replay 判决和诊断错误码放在同一字段，调用方难以知道该按哪套域解释。

收敛后，判决放 decision，诊断放 error_code，根动作限定为已登记且不相交的 quota/frontier 并集。跨运行时绑定从 owner 生成；旧 v0 签名计划保留原字节语义，避免改写历史导致原身份核验失败。

同一改动还抓到 skip/quota_skip：消费分支存在，不能证明 producer 会输出那个值。需要追到支持位点上的真实赋值与返回，而不是把比较字符串也算作生产证据。

检查器也需要能推翻自己的反例

#4687 保留了评审中有价值的反例，修复三种“自信地答错”：全局重绑定被漏掉，字典 spread 后修改仍被当成旧初始化值，遮蔽的 String 被误认成内建转换。

这里误报与漏报的代价不同。保守扩大候选值可能多报一个问题；漏掉真实生产值，会让未登记输出通过检查。没有把握的动态形式应留下 unknown。

检查还要有扫描覆盖下限，不能靠少扫文件过线。后来删除持续膨胀的已提交 inventory，改成按需计算全树清单，也没有取消这个义务。当前支持形式之外仍有缺口，跟踪 issue 继续保留。

8. 长程任务语义：当 resume、monitor 与 replan 组合运行

在跨越数小时乃至数天的任务中，resume_when、continuous_monitor、自主 replan、hard_lease 与 quota 结算并不是彼此孤立的功能开关，而是在共享 AuthorityStore 版本号与只追加 rollout 回执之上联动的状态机。在 TypeScript 内核接管它们的组合语义之前，单个原语各自的顺风路径都能跑通，但两两或三方同时触发时却会让 Agent 陷入死锁——触发 heartbeat_receipt_identity_conflict、malformed_settlement_state、Vision 等待饥饿，甚至误杀整个会话队列。

就连统一轮次信源（C1）的过程本身也验证了有界切片的必要性。一次性改动 215 个文件的单体 PR #7430（C1: unify work sources and validate recovery）合入仅 7 分钟便在 #8265 主动回滚，以便在主干上逐项核验集成与成本边界。随后工程将其拆解为约 25 个独立切片——重新合入信源统一底座（#8211）、切换配额信源（#8956）、收敛统一 CLI 结算编排（#9004）、绑定 C1 重规划捕获摘要（#9022）——最终在 #9176（Default to Complete Turn and retire legacy delivery selectors）与 #9328 平稳完成默认切换。

按作用域续跑：resume by todo

todos/resume_condition.ts 在单次 todo.read 事务（#6874）中与 Goal 级 Vision 等待覆盖（#7298）协同，用带时区的微秒时钟与严格代际围栏统一求值 5 类闭集条件（todo_done、monitor_changed、pr_merged、capacity_available、resume_at）。真实运行推动了三组关键边界收敛：

  • 按精确作用域唤醒等待任务（#8231）：当同一个 Monitor 同时盯守多个 PR 或实验时，旧实现只要 PR A 发生变化就递增全局代际，导致等待 PR B 的挂起任务被提前误唤醒。todos/monitor_scope.ts 引入 monitor_changed:<id>@<scope> 与按 SHA-256 键控的分作用域代际表，单监控上限设为 128 个作用域——超限时明确拒绝第 129 个注册，绝不驱逐既有等待者的基线证据。

9. 对等协作：为什么“已返回”不等于“已完结”

当一个 Agent 把子任务委派给对等同伴或管家 worker 时，消息送达只是传输层事件——既不代表子任务已经完结，也不代表委托方已经采纳该结果。LoopX 在 collaboration/result_publication.ts、inbox_receipts.ts、inbox_read.ts 与 return_delivery.ts 中把传输投递、未完余量声明、委托方采纳与 Goal 成果托管权严格拆开：

  • 不可变的部分返回链（result_publication.ts，#8139）：结论更新通过 previous_result_key 串成不可变的哈希校验链（conclusion → conclusion-00000001）。#8139 引入 return_format_version: 2，对 text + remaining_work 合并执行 20,000 字符预算，同时在重放时保留旧版字节格式，防止崩溃恢复时宿主校验哈希漂移。
  • 结果审阅不消耗单次执行预留（#8329）与对等结算隔离（#8853）：conversation_binding.ts 中的 planWorkAfterResultReview()（#8329）确保只读的中断结果审阅轮不会提前烧掉可写 owner 的 work-1 预留名额，待可写 owner 接手并复核原生副作用证明后再续跑剩余工作；#8853 则在单通道结算时按显式 agent_id 过滤 projectSettledReplanHistory，防止同伴漏记或损坏的语义回执死锁当前 Agent 的结算，而无作用域的全局 status 仍保留完整的多 Agent 健康检查。
  • 显式的 Goal 成果托管权移交（#9308）：当协作成员退役时，goals/outcome_requirements.ts 与 outcome_records.ts 将不可变的初始声明人 declaration_owner_agent_id、历次审查记录对象 recorded_for_agent_id 与当前负责人 owner_agent_id 分离，使本地 owner 能在成员表版本围栏保护下安全接管指定成果责任，而不篡改历史归属证据。

10. 调用方和默认值，决定迁移能否到用户手上

完整事务还要求调用方准确表达意图。前述 #4178 中，空白 note 表示不修改；显式空列表和 false 则是按对应字段解释的输入。不能把它们统一过滤为“没传”，也不能一律解释成“清空”。dry-run 要准确模拟，不能因为选定 provider 不可用就回退别处。随后 #4279 也收敛了读取分类与投影交付语义；部分 Python read owner 被有意保留。一个 owner 是否清楚，比为了语言纯度再造一份解释更重要。

新建默认值是另一个例子。当前 priority 回归保护以下区别：

输入或操作 预期行为
新建任务，省略 priority 使用新建默认 P1
读取旧任务，历史上没有 priority 保留历史含义
重放原创建 operation 返回原结果
只修改正文 保留已有 priority
显式清空 确实清空
结构化声明与旧正文前缀冲突 拒绝并给出修正上下文

这些区别由 File/SQLite 回归 保护。把“新建默认值”放在原回执恢复之后，才能避免升级替历史做决定。

最后一轮评审还发现：TS 核心的 metadata-only completion repair 可以通过直接测试，普通 Python producer 却会自动带上 completion policy 和 auto-acquire 等默认参数，被核心视为混入了新工作，导致 File/SQLite、dry-run/执行的实际入口都失败。公开反例 记录了这一点。

这个恢复缺口在基线也存在，不能全部归因给最后的贡献者。修复要走到普通调用方，同时继续拒绝真正的新正文、continuation、所有权或验证修改。直接构造正确 typed request，仅证明内层会处理它。

11. 恢复原结果，同时保护当前执行权

恢复最容易混淆两个时间点：原操作当时合法，现在的执行者是否还能继续改状态。

设想一次 team-plan 已经提交，响应丢了。升级后，调用者拿原 operation ID 重试，新准入规则却变严了。若先按新操作拒绝，就会把原成功结果挡住。最后的 恢复评审 抓到了这个问题。

当前路径先解码并定位正确权威，核验原身份、意图与回执。确属同一笔已生效操作，就恢复原结果；无匹配原结果的工作，再走当前准入。选定 provider 的可用性与证明仍需要成立，不能在故障后偷偷换到 Markdown。

返回原结果不会续租，不会覆盖后来提交，也不会复活旧 writer。租约转交、epoch 改变和后续状态，都有自己的保护。

类型也表达这种区别：历史解码仍认识 legacy，当前新执行的 handoff 配置只接受 soft_claim 与 hard_lease。旧记录可读、原操作可恢复、当前执行获准，各自有独立条件。

2.2.0 的 CLI 原子自认领（#7510、#7793）同样遵循这一边界：单条命令在 hard_lease 下原子完成认领与租约授予，并直接返回绑定当前 lease_epoch 的后续进度写回与完成结算命令；重放旧认领只恢复原回执，不隐式顺延已过期的执行代际。

内部回执保护的范围也有限。一次外部远端 effect 若没有可核验的幂等身份与回读，不能只凭控制面只结算一次，就宣称远端恰好执行一次。unknown 应在它实际发生的边界上保留。

12. 为 Agent 设计 CLI，而不只是给人类敲命令

面向人类的终端 CLI 默认操作者拥有跨轮次的带外记忆：人类记得自己刚传过 --limit 5，能肉眼识别陈旧缓存，会读异常栈，查看状态时不会顺手触发写操作，且多打印几千字节几乎没有边际成本。而大模型 Agent 是一个没有跨轮带外记忆、严格按字面解释输出、极易盲目重试、且按 token 与前缀缓存计费的状态机消费者。每一字节 stdout 都会进入提示词历史，改写早期历史会直接击穿前缀 KV 缓存，未标记的展示截断会被当成“剩余任务为零”，带副作用的预检或超时丢包则会诱发连环重试风暴。

单一 Turn 决策 owner 与可直接复制执行的修复命令

多入口各自拼装判断会导致“准入时放行、结算时拒认”的脑裂与盲猜参数循环。#4496 将 quota should-run、turn plan、turn run-once 与 turn managed-step 收敛至同一个决策 owner（build_fresh_turn_decision_owner → loopx_turn_envelope_v1），把准入时的状态快照、调度上下文与启动钩子原样带入结算。#7462 进一步把主动作指令选择迁入 TypeScript（work_items/interaction_contract.ts），在读取业务指令前先合成恢复优先级，并将 2.2 万行积压任务下的跨进程 RPC 载荷从 2,354,852 字节压降至 959 字节（通过 182 组字节级等价校验）。

当操作被阻断时，CLI 直接投影可复制执行的下一步命令，而非抛自然语言异常让模型猜参数：#4595、#4893 与 #6212 将未绑定回执（receipt_unbound）从身份冲突（identity_mismatch）中独立出来，并在存在前序欠账轮次时直接返回 owed_prior_turn 收尾命令；#8855 输出精确的纯重规划收尾与 no-followup 参数；#9136 保留类型化运行时诊断码与 quota_spent: false 账本证明；#9293 则把不可靠新建目录绕开的逻辑写域锁冲突（write_scope_conflict）与可通过独立 worktree 隔离的工作区冲突（workspace_lease_conflict）明确分开，阻止 Agent 徒劳创建无用工作树。

用密封的 projection_envelope 区分展示截断与源数据残缺

复盘 47 天内 5 次“健康信号全绿、顾问 Agent 却基于过期或残缺信源作答”的事故（#5087）后，#5085 引入了 projection_envelope.ts（sealProjectionEnvelope），并在 #6679 接入 quota should-run、在 #6874 接入单事务 todo.read。fresh、complete 与 alert 只能由 TypeScript 内核计算；命中缓存重返时只更新 served_at 而不伪造 observed_at；todo.read 则在执行 --limit 或精简切片之前的完整匹配集合上计算 coverage（expected_count、included_count、omitted）。单纯的展示行数截断标记为 truncated: true 且不触发误报，而信源未读或漏项则强制置 complete: false, alert: true——彻底杜绝模型把“只展示了前 N 条”误判为“所有任务已完成”。

保护前缀 KV 缓存与上下文窗口的经济学

接口预算合同及其 base/head 差分验证器（#6123、#9103 通过私有 Git 索引导出 origin/main 以消除路径长度偏差）在单任务、36 任务拥挤态与多 Agent 夹具上同时校验实际 stdout 字符数、UTF-8 字节、行数、单任务增长斜率、语义 JSON 键集与动作签名 SHA-256 摘要。自然语言义务须逐句核对：去掉 JSON 缩进使 36 个 Todo / 12 条 run 夹具的输出从 48,418 降至 39,726 字符（约 18%）且解码语义完全一致，而删掉一句权限限定词来迎合体积上限则是违规。

在单条命令体积之外，三项机制直接保护多轮会话的前缀 KV 缓存与轮次延迟：

  • 渐进子树摘要去重与只追加备注前缀证明（#7196、#8100、#8523）：不可变轮次快照固定原生首读，利用私有账本 SHA-256 摘要跨轮去重未变化的 >=1 KiB 子树，并为任务备注生成只追加前缀证明（<prefixBytes>:<sha256>，#8523），使进度追加只传输新增 UTF-8 后缀，同时强制每轮内联最新的控制指令、租约与版本号。
  • 保护前缀 KV 的任务语义单元折叠（stage-then-swap，#9213）：传统的滑动窗口或中段摘要会改写早期 token，导致整段后缀的前缀 KV 缓存全部失效。quota/stage_then_swap.ts 与 todo-unit-fold.ts 在任务启动时锚定 prefixNodeCount 与 prefixDigest；到达静默边界时，仅当早期前缀哈希完全未变、无跨锚点的工具调用配对、完结回执摘要有效、可选只读观察命令通过严格参数白名单且摊销净收益不少于 64 token 时，FoldToReceipt 才将尾部区间 [startSeq..endSeq] 原子替换为保留失败事实与未结义务的紧凑回执 μ，任一条件不满足立即无损回退至 KeepRaw。
  • 消除状态读取的 N+1 RPC 风暴（#7755、#9392）：决策路径跳过仅用于界面的全量日志扫描（#7755）；#9392 进一步将重复权威读取与随挂起任务数线性膨胀的 N+1 分页收敛为 1 次 todo.read RPC 和恒定上界 todo.context.page <= 5（0 个与 12 个挂起任务下调用数完全一致），并用读前读后日志状态与 todo_authority_head_verify_v0 封住中途并发改写的 TOCTOU 窗口。

严格的读写纯净性与 CAS / 幂等重放合同

Agent 频繁执行预检并在超时后重试，读操作与写操作绝不能混杂。#8685 将 quota should-run --dry-run 收紧为纯只读路径，把启动通知钩子、rollout 日志、轮询回执与缓存写入全部挡在 not preview 之后。#8776 在 run-once 发现已宣告的准备认领未被消费时前置拒绝（turn_execution_preparation_claim_not_consumed），实现零宿主拉起、零配额消耗。请求级 ContextVar 作用域（#4694、#6992、#9433）在单次逻辑请求内固定运行时指纹与钩子解码快照，不依赖挂钟 TTL。而在全部变更类命令上——handoff（#4094）、goal-acceptance（#7088）、task-lease（#8310、#9225 保留显式版本 0 的真实 CAS 语义）以及 todo 写操作配对只读 todo receipt（#9263）——--expected-revision 负责拦截并发陈旧基线，而携带同一 --operation-id 重试则精确重放原回执，既不重复执行也不自相冲突。

可恢复的文件，也不能当成模型的记忆

前面的恢复问题还在上下文交付中出现：一张旧回执不能续租，一份保存在磁盘上的完整基线也不能证明模型已经读懂其中的约束。

2.2.0 的原生文件差分把这两层分开：编码器核验同一有效周期内的完整文件、版本与 scope，准确还原当前结构；Agent 则从当前完整视图，渐进式读取本次判断需要的目标、要求与证据。即使收到 delta，也能直接选读当前事实，不必先读完整旧基线。压缩发生在未结束的工作中时，补回缺失事实，同时保留原任务与结算身份。

这项边界让“文件可还原”和“模型掌握了什么”各自可检查。具体的语音任务、JSON Pointer 与默认文件路径，见渐进与差分交付的完整例子。文件与读取路径成立，仍需继续检验它们是否改善了真实研究。
