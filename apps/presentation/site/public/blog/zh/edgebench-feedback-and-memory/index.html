让 Agent 多做十小时，究竟多做出了什么？

EdgeBench 如何反过来改造 LoopX 的长程控制面

一项研究可以起步更好，却在接下来的十小时里几乎没有增长。也可以不断改代码，最后丢掉最好结果。我们用这两种失败，重新审视目标、反馈、实验步长与恢复。

这条研究从 10 月初的轨迹诊断开始，先修评测与续跑，再追踪证据怎样进入下一次实验，最后把控制面自己的成本算进来。下面按这个过程展开：哪些机制改了，哪些结果支持它，哪些结果迫使我们改方向。

研究时间线可信反馈目标不丢实验步长完整恢复后程结果总成本

这里的 kernel 指 LoopX 共享的目标、准入、事务和恢复规则。LoopX 让原始目标、验收条件、工作归属和证据跨会话、跨宿主持久化。控制面约束状态转换，为模型的下一步提供反馈，但不能认证这个选择是否高明。一条发现、一次读取回执、一条 replan 记录都只是中间证据；真正需要追踪的链条，要落到实际工作和经过验证的成果。

这些规则的归属和强模型参与的语义修复，见 TypeScript 重构一文。下面从研究过程检查这些规则怎样影响实际工作。

  1. 目标验收与范围
  2. 证据结果与限制
  3. 决策继续或换方向
  4. 工作执行与验证
  5. 保留保住最佳有效成果

我们区分起点优势、后续增量和最佳成果保留。更高的最终分数，可能主要来自更强的起点；更好的中间候选，也可能没有留在终态工作区里。运行更久、Todo 更多、图更大，都不能替代这三项判断。

2. 先确认反馈值得相信

最初的 Portfolio 实验先暴露了测量和执行缺陷。一个盲跑 wrapper 在移除评测入口时，也删掉了迭代优化提示；一个账本检查把更早的市场收益归给了收盘时才买入的持仓。它们都混淆了原本的比较。修复后必须另起尝试，旧结果继续保留。

一个小反例就能说明记账问题：初始现金 100,000，在收盘价 200 时买入 100 单位并支付 10 手续费，即时权益应为 99,990，NAV 为 0.9999；新持仓没有赚到此前从 100 涨到 200 的收益。之后，对两个冻结样本独立重建，各自 243 天全部吻合，权益残差小于 4×10⁻⁹，股数没有差异。这证明账本一致，不证明投资策略优秀。版本化修复见 EdgeBench #14。

续跑也有类似问题：某个工作项结束后，外层进程可以不断唤醒，却没有恢复出有用的下一步。判断必须回到原始目标。Todo 完成之后，可以继续实验、等待或结束，但它本身不能代表 Goal 验收。可靠反馈与恢复让之后的研究变得可解释。

长任务没做完，何时检查方向？

一个证明任务可以连续做几个小时，Todo 始终处于进行中。如果复盘只在完成若干 Todo 后触发，最需要检查的长任务反而可能一直等不到检查。把任务人为拆碎来凑次数，也不会改善研究。

10 月 7 日的 #5879 改了计数依据：按照已经结算的有效工作 Turn触发复盘，同一个 Todo 尚未完成时也能检查方向。这不是每调用一次工具就复盘。只写入进度而未完成结算，不增加次数；重复历史也不能重复计数。原有明确的 Todo 单位设置继续保留，各批实验仍按自己的冻结配置分析。

另一半修复在复盘之后。判断现有方法仍然可行，可以带着证据继续原任务，无须为了证明“重规划过”而换路线。该合入版本的真实 CLI 回归覆盖了同一未完成 Todo 上的结算计数、缺失结算回执时不计数、拒绝没有证据引用的复盘，以及有证据地继续后再次获得工作准入。它验证了检查方向的时机与恢复执行的路径；模型是否作出更好的选择，仍要看后续实验。

比较边界

历史研究包含 Official、单次调用、原生 Goal、LoopX Resume 和 LoopX Explore。Explore 在续跑基础上增加可选的证据采集和规划。盲跑仍可使用公开任务、训练数据和本地验证器，但收不到隐藏评测分数和诊断；后台操作者评测不是 solver 反馈。后来的 native-feedback 研究由 Agent 主动申请评测，按已接受提交执行一小时冷却，不做周期评测。这些是不同研究，不能合并成一个处理效应。

模型、effort、提示、runner 和预算共同演化。早期主要用 Sol/xhigh，后来的 Sol/max、Astra/xhigh 批次各自保留条件。每臂一次运行只能提供描述性证据。缺失、主动停止、无效和有效零分分别记录。Checkpoint 接续保留源时间、评测机会和冷却；donor 历史不算新的独立重复。

3. Agent 完成了自己列的任务，却没完成你的目标

长程研究的一个危险漂移是：原目标要求改善算法，Agent 把它拆成“实现方案、跑测试、提交结果”。三项 Todo 都完成了，外层循环也结束了，但算法是否更好仍未得到回答。另一个漂移来自 Agent 自己加的筛选门槛：某个局部 proxy 不过线，就被升级成不能继续研究的硬限制。

#6133 把原始目标和硬约束，与 Agent 的暂定候选条件区分开；要求有区分力的实际产物证据，并保留适用范围明确的负结果。#6199 将原始研究任务贯穿启动、Goal 与恢复：实现、测试、提交都是里程碑，不能替代目标验收。到 #6649，检查又深入到真正送进 replan 的内容——不能用泛化提醒替代原问题，也不能把有用的 scoped evidence 截成短尾巴。

把目标存进文件，只解决了“找得到”；把它完整送进下一次决策，才有机会约束“接下来做什么”。 期限与停止仍由宿主执行。保留目标不等于允许无限续跑，也不保证模型一定找到好方案。

4. 失败之后，应该做小一点，还是换一个问题？

如果失败后总是缩小步长，Agent 很容易陷在局部修补里。一次失败可能来自实现错误，也可能说明整个机制假设不成立；这两种情况不该得到同一个“做少一点”。

#6298 先把工作规模、路线距离、验证范围分开。随后 #6321 将 grow / hold / shrink 的机械映射改为 grow / switch / verify：扩大已有根据的路线，切换被反证的机制，或者补一个能分辨假设的实验。每条路线需要自己的具体计划，工作单元要足以完成一次有效检验，不能只缩短每轮文本。

例如一种求解策略只在高重复输入上有效，合理下一步可能是验证收益是否跟重复程度相关，再决定是否采用选择器；也可能是保留旧策略。这个例子说明三种决策的区别，不是声称某一 PR 已证明通用收益。Explore 记录的发现还要回到后续复盘，看它是否被采用、带来新信息或改变了实验。没有必要为了增加“转向次数”而强行换路线。

这些是可选的规划机制。启用它们之后，仍需验证真实决策和后续成果；一个已登记的实验计划不是效果提升。

5. 恢复一次研究，要恢复哪些东西？

复制候选代码，只保住了研究状态的一部分。如果接收者忘记已经用过的评测机会、从零计算冷却时间，或把恢复耗时从预算里抹掉，“同点接续”就悄悄获得了额外资源。

#6305 将会话、候选、Explore、Goal、评测 best、机会、冷却和预算一起纳入 checkpoint。先暂停写入并封存，再允许围绕该状态做决策。#6622 把 fresh-session 切换提前到复盘之前：否则关键路线已被旧上下文选定，随后换会话无法回答“新上下文怎样影响这次选择”。

这个恢复合同支持更有针对性的比较：同一研究点之后，两臂读到了什么、选择了什么、实际跑了什么、留下哪个有效结果。它不能自动消除模型、effort 和 runner 差异，也不能把同一个 donor 的接续当作新的独立重复。未知的恢复资格继续保留为未知。

6. 十几个小时之后，是起点优势，还是新的进展？

Schema：起点领先不等于持续改善

Schema 是这里展开的反例。Sol 新旧版 14 小时窗口，新版 0.804620、旧版 0.723684。但第一次原生结果已经是 0.794620 对 0.713158，且收到反馈的耗时不同。后续增量仅为 0.010000 和 0.010526。较大的终点优势主要来自起点；后续不断改代码，仍未完成原始六项目标。

另一组 Astra/xhigh 的 12 小时比较更不利：Official 达到 0.881813，LoopX 为 0.786257，两边 6h 到 12h 的 best 都没有提升。LoopX 记录了 36 次完成的压缩，Official 为四次；未缓存输入约为其 5.32 倍。压缩可能与有效工作重叠，版本、恢复、共享负载和评分条件也有差异。但轨迹仍指出了实际挑战：更多改动和控制活动，没有转化为更多验收价值。

这些窗口的条件与限制

Sol 新旧研究采用 planned + Explore、Sol/xhigh、关闭 TurnEnvelope、Agent 主动申请 native feedback、一小时冷却。14h 是读过早期结果后，按最早实际结束时间以下的最大整小时选定，并非完成 18h。另一组 Astra 比较各臂自己的前 12h，包含准备。Sol 窗口对齐了 7,522 个独立 response 和 52 个收到的原生结果，Astra 为 5,277 个 response、45 个结果；累计计数没有反复累加，reasoning 已在 output 中。历史基础设施失败及整次运行完整性未知继续保留。处理包不同、自适应重启，以及此前操作者读到过一个 Official 终态汇总，都限制了因果判断。

7. 控制面自己花掉了多少成本？

另一个错误假设是：入口 packet 变短，Agent 的总成本就会下降。把目标、事实、写回说明从入口挪到第二条命令，确实缩短了首屏；模型随后还要读取它们。若中途丢失上下文，又要重建同一份来源。只量入口，就把成本移出了表格。

#7269 将原有捕获交给共享的上下文 reader：先读完整目标、事实和反馈，再读写回格式及结算步骤。review 与 writeback 是同一个不可变决策的两个视图，不是重新做一次准入，也不各自拥有一套权限判断。源码回归逐项核对目标、规划范围、证据引用、完整写回合同和 action signature；小入口必须仍能到达完整义务。

差分还增加了一个前提：接收者确实保留了那份精确基础。当前 native Hook 路径在同一会话和 context epoch 内，把完整分页后的正常工具交付作为连续性工程假设。会话变化、已观察到的压缩、缺页或已知交付失败会使它失效，随后读取原来的完整 capture；另开一次 guard 取得的新决策不能代替恢复旧决策。漏掉的 Hook 和不可见的下游截断仍是限制，读取回执不是模型保留内容的独立证明。

同一 PR 的一组历史离线对照把所有必读阶段重新加总。以下固定比较基线 59464f974 与测试 head a006a2bea1、同四份保留观察的交付；它不是最终合并 head 的重新测量。

把结构输入单独计量

LoopX 输入占比 = LoopX 相关 packet 的实际输入 tokens 之和 ÷ 全部模型实际输入 tokens 之和。 两者须覆盖同一请求集合和窗口，重复回执去重；另一次请求重新消费同一上下文，则是新的实际成本。

分母包含缓存与未缓存输入，缓存部分及归因覆盖单列，不平均逐请求百分比。只有总输入、没有 packet 实际归因时，占比仍未知，不能填零，也不能由字符或传输字节换算成“实测 token”。结构占比本身还不是净效率损失：它是否减少无效工作、帮助保留成果，要与完整成本一起判断。

较早的字节对照与撤回的测量

历史离线回放说明了为什么必须算总量：结构化 Host 和原生呈现字节下降 57.72%、60.23%，原生入口加完整恢复上升 6.37%。这些是历史字节观察，不是当前提交的模型 token 结果。早期离线探针还曾报告 CLI 字节增加 2.25%，但因漏掉最终 CLI 压缩并重新格式化入口，已撤回其实际 CLI 交付测量资格。该数字仅作为无效历史记录保留，不用于完整交付或成本结论。不能把视图缩小 60% 写成总成本下降 60%。

当前效率工作把普通入口、分段交付接到共享传输，减少重复读取和重新绑定，消掉可避免的结算往返。差分关闭的默认路径同样重要；开启后也必须正确恢复，并让产品和 benchmark 都易于启用。所有机制合计 15% 的参考目标尚未完成资格验证；它不是每个机制各有一份额度，也不能用来漏记失败和重建成本。

同点接续：完整结果与用量

证据有没有改变下一步工作？

成熟 checkpoint 可以帮助观察一个具体决策边界。接收者继承相同科学状态和 incumbent，再追踪它读了什么证据、选了什么实验、实际做了什么、原生反馈如何。负向本地结果若能在明确条件下排除一条分支，也有价值。继续原方向有依据时，replan 不必强行改道。

近期 #7269 让 Agent 先读目标、事实和反馈，再读写回格式；释放过时的任务选择偏好，并在创建 successor 后保留原 Turn 的结算身份。它对应两个真实往返来源：决策前先读大段写入指令，以及后续任务创建后还要补一轮确认结算归属。

近期实现细节：放回它们所属的阶段

新路线已确定，原来的工作怎样收尾？

一次长程工作可能在复盘时发现：原路线的证据不足，应该登记一个新的验证任务。后继 Todo 已经创建，但这轮复盘的结果还没有写回和结算。如果再次读取准入就改选新 Todo，模型会面对两份身份：刚做完的复盘属于旧 Turn，新的工作却被投影成当前任务。多叫醒一次模型，并不能解决这项归属冲突。

#7269 收敛的是控制面的接续语义。创建后继任务证明路线已经落地，不证明原 Turn 已经结算，也不授予新任务执行权。 原有 TypeScript replan transition 和 quota settlement owner 保留创建回执、原义务与原 Turn 的绑定；同轮重读返回原结算步骤。写回后只剩待结算步骤，结算后这轮停止，新任务保持 open，留给下一次正常准入。

这里还必须区分 must_attempt 和 delivery_allowed：前者要求处理本轮的工作义务，后者描述普通交付是否获准。需要重规划时，即使普通交付关闭，合法的规划工作仍可继续；不能为了让 Agent“动起来”就打开普通执行许可。租约、预算、停止条件和后继任务的准入继续由原 owner 判断。

真实 File / SQLite CLI 回归先创建后继，再原样执行返回的写回和结算命令：提前扣额被拒绝，重复结算只有一次 debit，原 Turn 不被后继替换，下一 Turn 才选择新任务。另有归属改变、延后和撤回 claim 的负例，证明失效的创建回执不能结算原结果。这里验证的是完整状态转换和真实入口，不能由一个字段或一次 ACK 代替。

这项修复让模型把注意力留给“接下来验证什么”，减少为结算身份反复解释和重新准入的机会。它没有保证下一项研究一定有效；我们仍要追踪证据、选择、后续实际工作和原生成果。同点接续观察给出了有限正向结果及其反证。

一次读取，为什么重复检查同一份运行时？

有些开销来自控制面自己。读取一页 Explore 研究上下文，需要多次调用同一个受管理的 TS runtime。Python transport 每次调用都核验运行时源码指纹；在包含大量量化发现的请求里，同一份源码树被反复检查。慢的是这一条真实控制路径，不是模型推理，也不是研究算法。

#7013 复用已有 effect_runtime_request_scope，把 explore_turn_context 包在一个逻辑请求内。同请求只解析一次 runtime revision，内部调用使用相同代码版本；离开请求时在 finally 中释放并重置，下一次读取重新解析。复用的是运行时代码身份，不是跨请求缓存 Goal 状态或研究结果。 共享规则仍由 TS owner 执行，Python 只收敛 transport 的重复工作。

原 PR 对 600 条合成发现执行真实隔离 CLI：单独预热后取三次未插桩样本，中位数 File 从 4.005 秒降至 0.495 秒，SQLite 从 4.268 秒降至 0.603 秒；环境为 Node 24.21、SQLite 3.53、Python 3.14.8。完整 JSON 与来源日志字节一致。这是具名历史负载上的 Host 延迟，不是当前版本复测或整轮 Agent 的八倍提速。

回归还独立检查：下一次请求能读到新 finding；损坏历史继续报错；失败后 scope 已清除，修复来源后的下一次读取可恢复。旧实现会在“一次请求只核验一次”的反例上失败。单纯加一个永久缓存虽然也可能更快，却会失去这些边界。

这类优化的直接价值，是更快拿到同一份决策输入，同时保留下一次请求的新鲜性。更少墙钟等待是否换来更多可验证成果，仍需要完整工作轨迹；本例没有测出更少模型输入或费用。
