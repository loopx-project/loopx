LoopX’s TypeScript Semantic Control Plane: Transactions, Task Semantics, and an Agent-Native CLI

LoopX is, at its core, a general-purpose long-horizon task semantics engine—not a prompt wrapper, static DAG, or generic microservice queue. When an effect succeeds before its checkpoint lands, a resumed Agent outlives its task lease, or a truncated CLI view looks identical to finished work, conditional continuation, continuous observation, evidence-driven replanning, peer handoffs, and Agent-native CLI output must compose inside one TypeScript state machine.

Retrying an operation can execute its effect twice; reading back a success receipt can revive execution rights that have already expired. Across runs spanning hours or days, a general-purpose long-horizon task semantics engine must make conditional continuation, background observation, evidence-driven replanning, peer handoffs, prefix-KV-safe CLI interactions, and transactional state across local SQLite and cloud PostgreSQL composable and verifiable for long-horizon agents and agent teams.

1. The semantic questions we put stronger models to work on

We use stronger models in design, implementation and review, especially to trace assumptions across files and runtimes. The difficult cases often combine individually reasonable checks into an unsafe execution order. Core PRs in August and September already dealt with these problems; they were part of the migration itself.

The effect happened, but its checkpoint did not. Is retry safe?

A provider succeeds, then the process crashes before writing the checkpoint. The journal says unfinished; a blind retry may execute twice. Treating every uncertain result as success would instead lose work that never happened. A try/catch cannot settle that distinction.

On August 22, #3485 introduced a durable prepared attempt and stable effect identity before execution. Recovery asks the provider: confirmed committed means checkpoint the original result; confirmed absent permits execution with the same identity; unknown remains pending recovery. Effect order, receipt prefixes and identity checks remain part of the contract. This is not arbitrary external exactly-once execution: confirming the result depends on provider recovery support.

This complements the preflight in #3464. Before execution, determine whether the effect is allowed; after interruption, determine whether it already happened. Moving Python functions to TS one at a time does not protect both boundaries.

On September 13, #4286 converged receipt recovery for seven Todo operations on one owner while retaining a finer distinction. Suppose two agents update a task: A commits first; B receives a definite version-conflict rejection, then loses its connection while reading the receipt. The later read failure must not erase the earlier rejection. If the connection drops before the commit response arrives, the result remains uncertain and recovery must use the original operation identity.

Both paths can encounter a network error, but they require different next steps. The shared implementation attempts the write once, then reads the original receipt. Its regressions distinguish conclusive rejection, commit uncertainty and exact-receipt recovery. Shared error handling must retain the phase of failure and facts already established.

Claiming work and acquiring execution rights must commit together

Two agents see an unclaimed task. If the claim is written before the lease is acquired, who owns the intermediate state? If an earlier claimant returns with a receipt after its lease expires, may it keep writing?

From the coordination foundations in #3529 and #3669 to the September 6 transaction in #4032, claim, lease and operation receipt converge on one conditional commit. The #3798 store owns atomic persistence; the domain owner checks identity, scope and legal transitions. A receipt proves a past claim succeeded. The current lease and epoch determine permission now. Replay must recover the original result without reviving expired execution rights. Storage revision, domain revision and lease epoch remain different identities.

Idempotency therefore requires more than returning an old success. Recovery must remember history and respect present authority. Foundation, shadow and production qualification arrived in stages; the first interface merge did not establish deployment of every backend.

Why could correcting evidence restart finished work?

A planning update corrects evidence without changing monitor state. Rebuilding the object from defaults can accidentally rearm an already satisfied monitor. Conversely, an explicitly empty list or false cannot be interpreted as an omitted input.

On September 10, #4178 converged planning updates on one authority snapshot and a complete TS transaction: omission retains intent, explicit clearing follows field and authority rules, and evidence correction does not rearm a satisfied monitor. It also removed Python’s serialize-to-Markdown-and-parse-back route. This repaired behavior as well as consolidating ownership; describing it as a mechanically equivalent language translation would miss the point.

Song’s #4433 and #4494 extended this discipline to vocabulary definitions, actual producers and consumers. A compiling enum does not establish that all callers mean the same thing. The skip / quota_skip example in the Semantics section and separation of action from decision belong to this same thread.

Making a plausible model answer face a counterexample

Ask for the mistaken assumption, then an execution sequence that refutes it: disconnect after commit, replay an expired lease, correct only evidence, explicitly clear a value. Check the real owner, provider and caller.

Stronger models help connect scattered conditions; counterexamples, real storage and refusal paths constrain their answers. There is no per-PR model comparison here, so these examples cannot quantify a particular model’s independent contribution. They show the mechanisms and reasons for changing them. Later runtime routing in #7145 and original-Turn closeout in #7269 continue this work rather than defining its whole history.

2. Reconstruct the history: from migration plan to task semantics engine

The formal migration RFC merged on August 15 (#3226). Over the first two months through mid-October, the program migrated core transactions to TypeScript and retired ordinary legacy Markdown writers in #6396. Through late November, a second convergence wave built directly on that transactional kernel: composable task continuation, background monitoring, and replanning; peer delegation handoffs; closed-set vocabulary ratchets; and an Agent-native CLI.

The three-developer-and-agent relay in #6396 closed the dual-writer transition so later task, collaboration, and CLI state machines could rely on a single authority owner.

Our new maintainer, Song (@songoow), has also been advancing the Semantics RFC, vocabulary convergence, production evidence, and checker fixes since mid-September. That track belongs alongside the transaction, task-semantics, and CLI story.

At its core, LoopX is a domain-neutral, general-purpose long-horizon task semantics engine for long-horizon agents and agent teams. Models propose routes; the engine protects versions, execution leases, composable task transitions, and state commits, then locates a valid recovery position after interruption.

Much of the original implementation was Python. TypeScript hosts, Pi integration, and the dashboard already existed. A Python call to make a decision, followed by a TS host consuming the result, was a natural starting point. As the system grew, defaults, state interpretation, ordering, and persistence could become distributed across both runtimes.

We wanted clear typed ownership of control-plane rules and contracts shared by the CLI, hosts, and App. The 103-day history developed through overlapping stages.

Plans can change usefully. The important record is why the route changed, which slices cut over, and which remained references or candidates. The maintained TS RFC retains those checkpoints.

3. Start with the Effect Program: agree on what happened

The first bounded cutover was #3416 on August 21. TypeScript took ownership of the Effect Program, settlement algebra, Turn-journal interpretation, and a durable checkpoint effect.

These boundaries fit together because recovery asks one connected question: which effects belong to this operation, which have committed, and what may happen next?

A checkpoint involves more than writing JSON to a file. Operation identity, same-key exclusion, matching the previous content, atomic replacement, and durability ordering determine whether a retry can recognize the original result. Splitting the rules across runtimes makes the next recovery fix harder to locate.

The cutover therefore moved internal effects and their rules into TS. Python retained compatibility calls and callback/provider boundaries. A managed local runtime starts on demand and exits when idle, with a private token and source fingerprint for lifecycle handling. Callers do not need to manage a separate daemon manually.

The design also had a cost. The PR reported these measurements for the same historical checkpoint workload:

Path p50 p95
Previous checkpoint 0.755 ms 2.020 ms
New durable checkpoint path 12.597 ms 18.610 ms

The new path added RPC and durability work. This records the cost of that first slice. It does not isolate language performance or describe today's complete CLI latency. Acknowledging the cost made it possible to assess whether later complete transactions removed more round trips and repeated interpretation.

4. Migrate a complete transaction: two calls can be right

On August 22, #3447 explicitly stopped flat leaf-helper migration. Adding a facade, DTO, and parity scaffolding for each function could make the production path longer while Python still owned composition.

The new unit was an observable transaction. Turn settlement connects decoding, identity, the journal, pending effects, reduction, and closeout. Todo completion similarly connects admission, state, leases, continuation, and a commit receipt.

#3464 replaced seven leaf runtime calls with the coarse turn.settlement.reduce contract. In that delivered slice:

New provider work: TS preflight → Python provider / checkpoint → TS final reduction
Existing replay:   TS reduction / original-result recovery

Two calls and one call describe new provider work and replay respectively. The responsibility diagram does not count every call in the complete CLI.

Review caught an attractive but unsafe optimization: retaining only the final reduction. That saved a call, but malformed identity or journal state could be rejected only after an external provider had executed. The final design kept preflight. TS authorizes the exact pending effects; Python executes and checkpoints those effects before final reduction.

A correct check in the wrong position can fail to protect the user. Its order relative to an effect matters.

Later lease, Vision, monitor-poll, spend, and void slices followed the complete-transaction approach. Their migration economics must name the old rules removed, bridges added, happy and recovery crossings, scaffolding exit conditions, and correctness and latency through the full entrypoint. A net increase in code can be justified, but the extra code needs a purpose.

5. Shared authority: connect distributed storage to Agent execution

In parallel, shared-authority work progressed from wchwawa's coordination core, aggregate/provider foundations, and recoverable references to the TS AuthorityStore in #3798.

Two responsibilities need distinct owners:

  1. The domain owner decides whether a transition is legal and who may execute it.
  2. The store provides conditional commit, durability, and proof readback.

The current AuthorityStore exposes operations including storeIdentity, loadAuthority, commitAuthority, readReceipt, and scanCommitted. The store atomically protects the head, events, and receipts. A database adapter must not quietly become an independent owner of domain transitions.

Several identities protect different boundaries:

Identity Boundary it protects
provider_revision A conditional provider commit; its representation can be opaque to domain callers
authority_revision A version of domain authority state
lease_epoch The generation of an execution grant, fencing an old executor
Store identity / lineage Whether a read still belongs to the same authority history
Operation identity / receipt Whether this is the same committed operation and what it originally returned

For example, a PostgreSQL connection may fail after COMMIT. The write may already be durable. A provider must distinguish missing, unavailable, failed, and ambiguous durability. A missing success response does not establish a missing commit. Reading the original operation's receipt is part of recovery. The PostgreSQL candidate also retained its separate deployment and adoption boundaries.

An earlier Python executor served reference and coverage purposes. The unused prototype was later deleted, while actual native File and SQLite paths became the corresponding qualification targets. Transitional references need an exit condition; they must not become a second production authority by accident.

When storage commits meet multi-hour Agent execution

Keeping pure storage commits separate from domain transition rules paid off once multi-hour Agents ran continuously across interrupted sessions:

  • Incarnation-scoped history fencing (#3464, #8975): When a recreated goal reuses a logical identifier on one append-only log, un-scoped acknowledgments from a retired incarnation can falsely satisfy an open review gate; binding commit proofs to an immutable (goal_id, instance_id) pair isolates incarnations cleanly.
  • Separating lease renewal from concurrent mutation (#5805, #9257, #9487): Multi-hour tasks routinely renew execution leases mid-turn (now defaulting to 3 hours). Renewing a lease under the same epoch and idempotency key advances the lease version without invalidating an already-admitted turn settlement (#9257), whereas an expired or replaced lease grants authority only for zero-spend administrative closeout—never for continuing stale execution (#9487).
  • One state contract from local SQLite to cloud checkpoints (#4121, #4408, #9380, #8759, #9223): Periodic 64-commit snapshots and index-exact delta replay scaled from local files and SQLite (#4121, #4408, #9380) to tenant-isolated PostgreSQL recovery past 20,000 commits (historical adapter, #8759), before #9223 extracted server-side cloud storage behind a clean Apache-2.0 AuthorityStore SPI.

6. After SQLite: retained history needs a cost model

LIHUA919's #4121 connected an optional SQLite provider to the existing TS authority contract. A transaction atomically commits the head, receipts, events, and outbox. Domain claim and lease semantics stay with their owner.

Adding the database left three distinct engineering problems.

First, reading the current head should not scale with total retained history. #4408 replaced a full retained projection per transaction with verified periodic checkpoints and committed deltas. It converged codec ownership and added transactional, idempotent migration of the old format. Current reads, continuity recovery, and a full audit have different read scopes.

Second, measure writes correctly. #4778 separately observed logical write volume, cumulative WAL traffic within a window, and application-observed lock wait. Final database size cannot substitute for write-amplification measurement. A rehearsal also does not establish formal capacity or sustained-operation acceptance.

Third, object ownership during replay affects correctness. #4931 reduced copying, sorting, and encoding of unchanged subtrees, and stopped materializing unused full projections for receipt lookup. It also prevented a caller's mutation of a returned projection from poisoning the next replay basis. Persisted proof bytes remained unchanged.

Some paths improved substantially. Large-state latency, scan cost, and memory still had gaps, and the PR retained the unmet targets. Those distinctions are more useful than a single performance-improvement label for every path.

In October, #5805 changed unconfigured new-Goal defaults to canonical SQLite and hard leases. Existing Goals, explicit choices, and old operation retries retained their own contracts. A new default, migration of existing data, and retirement of old writers happened at different stages.

In early November, #7834 extended the SQLite store to own archived task history: when tasks complete or are atomically superseded (#5698), terminal items beyond a small active window (N = 5) move into SQLite archive tables, decoupling live status-view size from total historical volume while preserving exact ID lookup and receipt replay.

7. Song's Semantics and the Zero-Any kernel

Our new maintainer, Song (@songoow), initiated and implemented the Semantics RFC, registry, and commit-path checks in #4433, merged on September 15. He continued advancing convergence afterward. This track governs how concepts grow as the software changes.

Cross-language migration readily creates duplicate knowledge. The same state can appear in a Python Enum, Literal, TS as const, a presentation layer, and a conditional branch. Even if the strings match today, one location may gain a value or change its interpretation tomorrow.

The Semantics RFC checks traceable relationships: definition owner, value set, generated binding, producer, and interpreter or projection. Runtime rules remain with typed owners. The registry constrains and checks them without becoming another production rule source.

Four kinds of information in one field

#4494 addressed a mixed effective_action field containing quota decisions, frontier actions, replay verdicts, and diagnostic error codes. Callers could not clearly identify the domain to interpret.

The converged contract puts verdicts in decision, diagnostics in error_code, and restricts the root action to the registered, disjoint union of quota and frontier domains. Cross-runtime bindings are generated from an owner. Old v0 signed plans retain their historical meaning and representation, rather than being rewritten in a way that breaks original identity verification.

The same work caught skip versus quota_skip. A consumer branch is not evidence that a producer emits the value. Checks must trace actual assignments and returns at supported sites, rather than counting string comparisons as production.

Counterexamples for the checker itself

#4687 retained useful review counterexamples and fixed three confidently wrong answers: missed global rebinding, mutation after dictionary spread treated as the old initializer, and a shadowed String mistaken for the built-in conversion.

False alarms and missed values have different consequences. A conservative candidate set may report an extra problem. Missing a real produced value can let an unregistered output through. Unsupported dynamic forms must preserve an unknown.

The checks also need scan-coverage floors, so scanning fewer files cannot make the result green. Retiring an expanding committed inventory in favor of on-demand full-tree computation did not remove that obligation. Gaps outside supported forms remain explicit, and the tracking issue remains part of the work.

From registered vocabularies to the Zero-AST-Any ratchet

Two commit-time AST verifiers turned Song's vocabulary design (#4433, #4494, #4687) from a review guideline into an equality-anchored pre-merge ratchet across Python and TypeScript:

  • Closed-set vocabulary verification (#4494, #8184): Full-tree AST scanning verifies all 34 registered vocabularies and 62 owner symbols with zero conflicting semantic values, pinning coverage floors by strict equality so constraints cannot silently loosen. For example, #8184 removed a local handoff-mode copy and enforced a typed subset rule: historical receipt decoding still recognizes "legacy" records, while fresh execution admission accepts only active claim and lease modes.
  • Zero-Any structural ratchets (#4178, #6396, #9282, #9433): Every one of the 43 tracked control-plane module baselines now pins dict[str, Any] counts to zero, preventing untyped dictionary merges from silently re-applying defaults or dropping fields across runtime boundaries.
Why eliminating dict[str, Any] surfaced latent concurrency and replay bugs

Replacing untyped dictionary carriers with explicit record types repeatedly exposed hidden state corruption during the refactor itself. Earlier in #4178, retiring serialize-and-reparse planning updates stopped partial edits from re-arming finished monitors; later, typing state-refresh records (#9418) exposed stale registry snapshots surviving replay across route switches, and replacing untyped hook dispatchers (#9433) uncovered and fixed seven real request-scope cache, symlink-ABA, and rollback-invalidation bugs in the same PR.

8. Long-horizon task semantics: when resume, monitor, and replan compose

A general-purpose long-horizon task semantics engine proves its worth when primitives compose across hours or days. Conditional continuation, continuous observation, and evidence-driven replanning are not independent feature flags—they execute as a coupled state machine over shared state revisions and execution leases. When separate adapters evaluated them piecemeal via dictionary overlays and second-level clocks, each primitive passed isolated happy-path checks while their pairwise and three-way interactions deadlocked Agents: waking unrelated waiters, stranding unspent turn receipts, or starving replanning when routine tasks blocked. Moving task readiness (#6874), goal-level wait coverage (#7298), and unified turn execution (#8211, #9176) into one TypeScript kernel made cross-primitive invariants enforceable in a single transaction.

Per-target continuation and cross-lease handoffs

Resuming deferred work safely requires evaluating the full dependency graph in one atomic read (#6874, #7298) and scoping both wakeup signals and lease lifetimes to the exact target:

  • Per-target wakeup generations (#8231): When one shared monitor watches dozens of pull requests or experiments, advancing a single global counter on target A prematurely wakes tasks parked on target B. Tracking independent SHA-256-keyed generations per target—capped at 128 targets per monitor and refusing overflow rather than evicting existing waiters' baselines—isolates wakeups without losing state.
  • Separating foreign lease loss from same-agent continuation (#4094, #9304, #9488): Multi-hour turns routinely outlive a single lease TTL. Rather than treating every expired lease identically, the kernel checks who holds the successor grant: if another worker claimed the task, the interrupted turn closes out administratively at zero quota spend (#9304); if the same Agent re-claimed the open task in a higher lease epoch, a fenced takeover receipt preserves the turn identity while requiring fresh verification against current task and acceptance digests (#4094, #9488).

Non-blocking background observation

Continuous watches must observe external signals at zero routine quota cost without accidentally re-arming finished work or blocking interactive turns:

  • Partial edits vs. explicit clearing (#4178, #4335, #9249): Rebuilding task objects from defaults during an evidence edit can silently re-arm an already-satisfied monitor (#4178), while deleting an optional scope key without recording an explicit field-clear list breaks full-replacement storage validation (#9249). Pure observation-to-state reduction (#4335) keeps counter updates, omission, and explicit clearing distinct.
  • Isolating watches from foreground queues and model blips (#5450, #9155, #9320): Early polls shared receipt namespaces and session queues with foreground work, so a quiet heartbeat colliding with a due watch wedged recovery (#5450), human chats delayed due polls, and an upstream LLM blip during an adapter healthcheck could kill deterministic observation turns that never call a model. Dedicated background watch sessions (#9320) and model-free observation health paths (#9155) decouple routine watching from active execution.

Self-referential replanning and causal lineage

Replanning is uniquely hazardous because a replan turn mutates—or retires—the very tasks and triggers that authorized it:

  • Atomic task supersession and trigger survival (#4902, #5698, #8854): Replacing a stalled plan links successor tasks, retires the predecessor, and releases its execution lease in one commit (#5698) over a unified replan history reducer (#4902). When a monitor triggers a replan after repeated no-change polls and the Agent retires that exhausted monitor inside the replan turn, the live task trigger vanishes mid-turn—so the kernel persists the trigger reason as an immutable scalar fact on the turn receipt itself (#8854).
  • Settling the turn before derived goal stop (#7298, #8588, #9411): When a replan writeback closes the last open gap on a goal, naive state evaluation immediately declares the goal finished and halts execution—stranding the replan turn's own unspent receipt (#8588). Prioritizing pending turn settlement ahead of derived terminal stop, alongside strict schema stripping when upgrading preflight guards (#9411), ensures every replan closes cleanly.

9. Peer collaboration: why “returned” is not “finished”

When an Agent delegates a slice to a peer worker, message delivery is only transport—neither proof that the delegated work is finished nor proof that the requester has adopted it. Building on revision-guarded claims and handoffs (#3529, #3669, #4032, #4094), LoopX keeps transport delivery, inbox reply completion, per-update requester consumption, and goal acceptance separate:

  • Hash-chained partial returns (#3669, #8139): Workers frequently return an interim milestone alongside explicit remaining work and its wakeup condition. Conclusion updates form an immutable hash-linked chain under a 20,000-character combined budget, while replay preserves historical wire formatting so post-crash digest verification never drifts (#8139).
  • Read-only review isolation and per-Agent fault isolation (#8329, #8853): Inspecting an interrupted peer return does not consume the writable owner's execution reservation before native effect proofs are re-verified (#8329). Likewise, per-Agent turn closeout filters settlement history by explicit Agent identity so a peer's unrecorded or malformed receipt cannot deadlock another Agent's turn, while global status views still surface cross-Agent health (#8853).
  • Provenance-preserving custody transfer (#4032, #9308): When a collaborating peer retires, separating immutable authorship and per-review attribution from active ownership lets a local owner adopt open outcome responsibilities under a roster-version fence without rewriting who produced earlier evidence (#9308).

10. Callers and defaults determine whether migration reaches users

Complete transactions also need callers to express intent accurately. In #4178, a blank note means no update; an explicit empty list or false is interpreted by its field’s contract. These values cannot all be discarded as absent, or all treated as clearing. Dry-run must model that intent accurately. An unavailable selected provider must not trigger fallback elsewhere. #4279 later converged read classification and projection-delivery semantics. Some Python read ownership was deliberately retained. Clear ownership matters more than creating a second interpretation to pursue language purity.

Defaults expose similar distinctions. Current priority regressions protect these cases:

Input or operation Expected behavior
Create a new task, omit priority Apply the new-task P1 default
Read an old task with no historical priority Preserve its historical meaning
Replay the original creation operation Return the original result
Edit only the text Preserve the existing priority
Explicitly clear priority Clear it
Structured declaration conflicts with an old text prefix Refuse with actionable context

The File and SQLite regressions protect these cases. Applying new defaults after original-receipt recovery prevents an upgrade from making new decisions for history.

The closing review found another caller gap. The TS core passed direct tests for metadata-only completion repair. The normal Python producer automatically attached defaults such as completion policy and auto-acquire. The core interpreted them as fresh work mixed into a historical repair. The actual File and SQLite entrypoints failed in both dry-run and execution. The public counterexample records this.

That recovery gap also existed in the baseline, so it cannot all be attributed to the final contributor. The repair had to reach the normal producer while continuing to reject real changes to text, continuation, ownership, or validation. A correctly constructed typed request proves only that the inner boundary can handle it.

11. Recover the original result while protecting current authority

Recovery can confuse two points in time: whether the original operation was valid, and whether today's executor may continue changing state.

Suppose a team-plan committed but its response was lost. After an upgrade, the caller retries the same operation ID under stricter admission rules. Rejecting it as fresh work first can hide the original success. A closing recovery review caught that problem.

The current path decodes and locates the correct authority, then checks original identity, intent, and receipt. If it is the same committed operation, it recovers the original result. Work without a matching original result proceeds through current admission. The selected provider must still be available and its proof valid; failure cannot quietly redirect writes to Markdown.

Returning the original result does not renew a lease, overwrite later commits, or revive a retired writer. Lease transfers, epoch changes, and subsequent state have their own protections.

Types express the distinction too. Historical decoding still recognizes legacy; current fresh-execution handoff configuration accepts soft_claim and hard_lease. Reading an old record, recovering an original operation, and authorizing current execution each have independent conditions.

Atomic CLI self-claim in 2.2.0 (#7510, #7793) follows the same rule: one command atomically claims the task and acquires a hard_lease grant, returning progress and completion commands bound to the active lease_epoch, while replaying an old claim recovers only its original receipt without extending an expired generation.

An internal receipt also has a limited scope. If a remote external effect lacks a verifiable idempotent identity and readback, settling once in the control plane cannot establish that the remote effect executed exactly once. Uncertainty belongs at the boundary where it actually occurs.

12. Designing a CLI for Agents, not just shell users

A human shell CLI assumes an operator with out-of-band working memory: someone who remembers passing --limit 5, visually discounts a stale cache, avoids mutating state while inspecting, and pays almost nothing per printed byte. An LLM Agent has no implicit memory across compaction boundaries, interprets output literally, retries aggressively after timeouts, and pays in both context window and prefix KV cache for every stdout byte.

One decision source and runnable recovery commands

When check, plan, and execution commands assemble state independently, an Agent gets admitted at the start of a turn only to be rejected at settlement—triggering flag-guessing retry loops. Converging every turn entrypoint onto one shared decision snapshot (#4496) and moving primary-action selection into TypeScript (#7462, shrinking a 22,000-row backlog RPC payload from 2.35 MB to 959 bytes with 182-case byte parity) eliminated decision-to-settlement drift.

When an operation cannot proceed, the CLI returns copy-runnable recovery commands instead of prose tracebacks: separating an unbound turn receipt from a true version conflict and emitting exact prior-turn closeout commands (#4595, #4893, #6212), and distinguishing logical write-scope waits from directory collisions that an isolated git worktree can actually resolve (#9293).

Separating display truncation from task completion

After five incidents in 47 days (#5087) where an advisory Agent answered from stale or partial sources while health checks reported ok: true, #5085 introduced a kernel-sealed read envelope, extended to turn admission (#6679) and single-transaction task reads (#6874). Cached responses advance serving time without forging observation time, and task completeness is computed over the entire matching population before --limit slicing. Display caps set truncated: true without false alarms, whereas unreadable or omitted work forces complete: false with an explicit alert—preventing an Agent from ever mistaking top-N truncation for finished work.

Output budgets and prefix-KV cache economics

Since #2144, an interface budget contract and base/head differential verifiers (#6123, #9103) gate stdout bytes, line counts, per-task growth slopes, JSON key sets, and action digests across crowded multi-agent fixtures—for instance, stripping JSON indentation cut a 36-task output by ~18% (48,418 to 39,726 chars) with identical decoded semantics, while dropping an authority clause to pass a byte cap is forbidden. Three mechanisms extend that budget across multi-turn sessions:

  • Cross-turn subtree deduplication (#7196, #8100, #8523): Unchanged >=1 KiB context subtrees deduplicate across turns via SHA-256 digests, and appended task notes transmit only new UTF-8 suffixes (#8523) while keeping live revisions and execution controls inline.
  • Suffix-only receipt folding that preserves prefix KV (#9213): Sliding-window or mid-history summarization rewrites early tokens and invalidates the model's prefix KV cache across the entire suffix. Instead, LoopX anchors the prefix digest when a task starts; once the task settles cleanly, it folds only the completed suffix into a compact receipt preserving failure facts and open obligations—verifying untouched prefix bytes, intact tool-call pairing, and a net token savings floor before swapping, or keeping raw history atomically.
  • Single-read status convergence (#7755, #9392): Decision paths skip UI-only log scans (#7755) and collapse N+1 deferred-task paging into one atomic task read with pre/post revision checks against mid-read races (#9392).

Side-effect-free previews and CAS + idempotent replay

Because Agents preview guards before acting and retry after dropped connections, inspection and mutation must never blur. Read-only --dry-run previews fence off all notification hooks, rollout logs, and cache writes (#8685), while request-scoped snapshots avoid wall-clock TTL staleness (#4694, #6992, #9433). Across mutating commands—single-attempt command receipts (#4286), task handoffs (--expected-revision + --operation-id, #4094), goal acceptance (--expected-provider-revision + --operation-id, #7088), and task leases (--expected-version + --idempotency-key, where the key identifies the lease generation across renewals, #8310)—explicit CAS flags reject concurrent stale bases while resending the exact original request (including its original CAS version and parameters) replays the committed receipt without executing twice.

A recoverable file is not the model’s memory

The same recovery distinction appears in context delivery: an old receipt cannot renew a lease, and a complete baseline on disk cannot prove that the model has read and understood its constraints.

The native file-delta path in 2.2.0 separates those facts. The codec verifies complete files, versions and scope within a valid cycle and reconstructs the current structure exactly. The Agent progressively reads the current full view for the intent, requirements and evidence its decision needs. Even a delta permits direct selection of current facts without first draining the old baseline. Compaction during unfinished work requires recovering missing facts while preserving the original task and settlement identity.

This makes file reconstruction and model knowledge separately inspectable. The worked voice-task example explains JSON Pointers and the default file path. A working file/reader mechanism still needs evaluation against actual research outcomes.
