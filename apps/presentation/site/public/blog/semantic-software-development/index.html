Agentic Software: Infrastructure for Long-Horizon Development

Using LoopX to explore infrastructure for agentic software: preserve goals, evidence, and human feedback across sessions, and carry exploration into verifiable delivery.

When developing software with agents, I increasingly care about a short feedback loop that can keep running: from an idea to implementation and real feedback. As code generation gets faster, goals, validation, handoffs, and human attention shape how much useful work we can deliver.

Building LoopX has led me to frame this as adding goals, evidence, authority, and evolving plans to a recoverable execution system. This is a short introduction for software developers; the core architecture article develops the mechanisms.

Shorten the path from an idea to validation

For products shaped by outcomes and user experience, one person working with agents across design, implementation, use, and revision has two immediate advantages: fewer handoffs in the feedback path, and shared context for product and technical tradeoffs. A poor interaction can lead to coordinated changes in the interface, protocol, and tests, followed by another hands-on check.

This makes high-quality human reward valuable: people identify what matters and what remains inadequate; agents turn that judgment into the next piece of verifiable work. Reward here can mean a correction, acceptance criterion, or priority change. It need not be numeric and does not imply training model weights.

There are costs. Concentrated context makes independent review more important. Code output can grow faster than evaluation capacity and human review bandwidth. Specialization and independent judgment still make collaboration valuable. The engineering problem is preserving a short feedback loop while making validation, maintenance, and delivery sustainable.

A public case: carry a performance optimization upstream

Zheng Cai (@zigzagcai) described using LoopX as the workflow engine for an agent framework optimizing vLLM. The resulting change has been merged as vLLM PR #54951.

The optimization targets sparse-indexer prefill. Previously, each tensor-parallel rank repeated MQA scoring and top-k for the query rows. The change divides independent rows into cost-balanced contiguous slices. Each rank scores its slice against the full available key history, then all_gatherv restores the top-k indices in the original row order. It removes redundant computation without approximating attention.

The PR reports GLM-5.3-Flash on 4×H200, TP4, 1M input tokens, and C1 sequential requests: TTFT falls from 54.154 to 40.388 seconds, a 25.42% reduction; input-plus-output token throughput rises from 17,856.28 to 23,675.18 tok/s, a 32.59% increase.

The measurements use a 65,536-token batch budget, the legacy runner, an explicit FA3 backend, and four paired fresh-process A/B restarts. C1 total-token throughput is not saturated concurrent serving throughput. I have not independently reproduced the result, and this case does not isolate LoopX’s causal contribution. It shows an inspectable engineering delivery: the optimization, measurement conditions, validation scope, and upstream acceptance all have public artifacts.

Establish that the measurement exercises the change

The PR preserves an important constraint: the new path needs at least 16,384 × TP scheduled prefill query rows in the current batch. At TP4, an 8,192-token batch budget cannot activate it, even with a 1M-token accumulated context. Long context alone does not establish that the optimization ran.

The author reran the comparison with pinned baseline/candidate revisions and the same 65,536-token batch budget, and disclaimed attribution of the old tables to the current change. This gives agent development a stricter acceptance criterion: the artifact, active path, measurement configuration, and conclusion must agree. An attractive number cannot replace that evidence chain.

For long-horizon development, that is more informative than elapsed agent runtime. Profiling, comparing hypotheses, implementing a change, validating it, and responding to review must remain connected. Failure conditions and measurement definitions need to survive into the next round.

Add semantic properties to distributed execution

Queues, leases, event logs, revision checks, and retries make execution traceable and recoverable. They usually do not decide whether a recovered plan is still worthwhile, whether a test applies to the current revision, or whether finishing a local task satisfies the goal. Agent work brings these questions into the execution loop.

A person adds: “Mixed-load latency is what matters; do not trade correctness for speed.” That feedback needs to become a revised acceptance contract, an evidence boundary, and successor work, rather than another preamble in the next prompt.

LoopX’s Semantic Control Plane externalizes goals, work items, constraints, and accepted transitions. Models propose work from current facts; scope, authority, and budget are checked before execution; tools return observations; domain validators check results; the kernel checks identity, revision, and transition rules before committing durable state. Exhausting the task list means the current plan is exhausted, not necessarily that the goal is achieved.

The diagram describes responsibilities, not deterministic code for every semantic judgment. Models and people interpret evidence, form hypotheses, and make tradeoffs; deterministic rules protect expressible boundaries. Semantic execution engines and agentic software

In Agents aren’t software, Runta’s Guanlan Dai moves the fault-tolerance unit toward semantic execution state and the judgments worth preserving. The question is whether unfinished work can continue meaningfully after process recovery.

A distributed-systems qualification matters: conventional software already has concurrency, randomness, dynamic scheduling, and external failures. Agents add solution paths, tool compositions, and intermediate evaluations proposed by models during execution. The search path is open-ended; execution, validation, and commit boundaries must remain explicit. Existing systems engineering becomes more necessary.

My framing is that models and harnesses own interpretation, hypotheses, and tool loops; domain capabilities define valuable outcomes and validation; execution environments constrain resources and external reach; LoopX preserves goals, responsibilities, evidence, and continuity between them. Latency, reliability, cost, and scale remain measurable requirements. We must also check whether changing sessions or executors loses the grounds for action.

The whole can be understood as a semantic execution engine: inputs include goals and feedback, while outputs include accepted state changes. The term describes responsibilities. LoopX specifically provides the semantic control plane alongside models, harnesses, and execution environments.

Local and cloud execution can share work identity, evidence, and acceptance contracts while adapting their environments separately. Migration checks should cover dependencies, revoked write rights of old executors, applicable authority, and the current acceptance revision. A shared protocol supports continuity; cloud delivery still needs independent verification.

A distributed-systems view: make judgments committable state

Adding semantics changes the state model, commit conditions, and recovery unit. Storing a natural-language goal in a database still leaves these engineering gaps.

Preserve authoritative facts; rebuild their views

Goal revisions, accepted decisions, evidence references, responsibility, and commit receipts need stable identities. Boards, summaries, and suggested actions are consumer-specific views. Irreplaceable results and negative evidence still need preservation; a recomputable display does not make its grounds disposable. The LoopX state/projection contract separates those responsibilities.

Use versions and causality to bound evidence

A passing test should identify candidate rA, workload W1, and acceptance v1; a decision should identify its action scope. With rB or v2, retain the historical fact and reassess its applicability. Ordering messages establishes sequence. Safe action also requires what the evidence addresses and who may accept a change.

Reconcile uncertain external effects before retrying

Suppose an agent loses connection after submitting a GPU experiment. The remote job may be running despite the missing response. AWS’s idempotent-API design explains the value of request identity for safe retries. Use a stable request or job ID for readback; retain uncertainty if the provider cannot resolve it. Settling the control-plane turn once cannot ensure one remote launch. The core article’s Effect Program develops that recovery chain.

Consistency protects commits; it cannot choose the best design

Leases, revision checks, and stale-writer isolation can reject an obsolete executor’s writes. They cannot choose between two designs that both pass local tests. Protocols protect execution boundaries; models, validators, and people compare routes. Shared state should align facts and expose disagreements, with decisions accepted by explicit authority. The last write is not necessarily the best judgment.

Long-horizon work therefore needs three lenses: safety, whether authority and acceptance boundaries are respected; liveness, whether eligible work is adopted and waits can resume; and value, whether further effort closes acceptance gaps or reduces uncertainty. A system can reliably execute a poor route. Outcome feedback must keep testing the third lens.

Build a foundation for sustained autonomous delivery

To sustain that short feedback loop, I would invest in three foundations:

  • Composable atomic capabilities. Let agents perform real operations through CLIs, return identified results and errors, and read back external facts. Establish a complete small loop before expanding the capability surface.
  • Evolving engineering constraints. Put architecture boundaries, RFCs, tests, independent review, and release gates in the repository. Continuously refactor duplicate authority and code decay instead of accumulating patches.
  • Evaluation that keeps up with development. Preserve baselines, candidate revisions, workloads, budgets, and counterexamples. Separate cheap local checks from expensive comprehensive evaluations, and retain independent acceptance. More diffs do not automatically mean more useful output.

Across rounds, sessions, and executors, these constraints need to become inheritable state. Long-horizon autonomous development aims to advance valuable work when no human decision is needed, let a correction change subsequent actions, and wait, change route, or close the work when evidence is insufficient or marginal returns decline.

When those improvements are used to improve the development system itself, a system-level self-improvement loop emerges. The bootstrapping and RSI article covers that history and its limits. Sustained commits and self-modifying code alone do not establish capability gains.

Start with a goal you can evaluate

You do not need a large agent team first. Choose your own experimental repository and specify the outcome, development scope, budget, and release authority. For example:

Fix the workload and baseline, then research and validate one performance optimization. Preserve failed experiments and counterexamples. Record the candidate revision, measurement conditions, remaining gap, and successor each round. Changes to the experimental branch are allowed; release and additional compute spending require my decision.

Connect through the Developer Book, then use loopx doctor and loopx status to inspect the environment and connected projects. Check a complete execute–validate–writeback–continue cycle. After changing sessions, can the agent recover the goal, evidence, wait conditions, and your correction?

For a small task that fits comfortably in one session, an additional control plane may not pay for itself. It is more promising where you repeatedly rebuild context, prompt continuation, and reconcile facts. I want more accepted deliveries and less human attention spent keeping work continuous.
